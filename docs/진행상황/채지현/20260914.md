MR: `feature/back/guardian-api` → develop (병합 완료)

### 무엇을 만들었나

모니터링 파트의 **알림 수신자 조회가 사용할 데이터의 원본** — 가구와 보호자(Keycloak 사용자)의 매핑 CRUD.

| API | 동작 |
| --- | --- |
| `POST /api/devices/households/{houseId}/guardians` | 매핑 등록 (Keycloak UUID 참조) |
| `GET  .../guardians` | 목록 조회 — **PRIMARY 우선 정렬 = 알림 발송 순서 기준** |
| `PATCH .../guardians/{keycloakUserId}` | 역할·연락처·수신 여부 부분 수정 (null 필드 유지) |
| `DELETE .../guardians/{keycloakUserId}` | 매핑 해제 |

- 검증: 없는 가구 404, 중복 매핑 409, Swagger 문서화, 빌드·테스트 통과
- 구현: 복합 키(house_id + keycloak_user_id) 엔티티(@IdClass), 부분 수정 업무 메서드

### 설계 근거

- **사용자 신원은 저장하지 않는다** — 이름·이메일·비밀번호는 Keycloak 소관. 우리 DB에는
  `keycloak_user_id`(UUID)와 서비스에서의 관계(가구·역할·알림 연락처)만 둔다 (ERD 원칙)
- `notify_phone`은 예외적으로 우리가 소유 — 알림 발송은 우리 서비스 기능이므로
- 테이블(`household_guardians`)은 V2 마이그레이션에 이미 존재 — 이번 MR은 API 계층만 추가

### 모니터링 파트와의 역할 구분 (팀 공유)

monitoring의 `HouseholdAccess`와 겹치지 않음:
- `HouseholdAccess` = "누가 이 가구 **데이터를 볼 수 있나**" (조회 권한)
- `household_guardians` = "누가 **알림을 받나**" (연락처·역할·에스컬레이션 순서)

알림 수신자 조회 진입점: `GET /api/devices/households/{houseId}/guardians`
(notifyEnabled 필터링은 소비 측 책임)
