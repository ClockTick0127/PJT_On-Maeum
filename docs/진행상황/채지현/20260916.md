# 진행 상황 회고 (0916, 채지현)

## 오늘 한 일 — 회원가입·로그인 API 및 가구 초대 코드 구현

브랜치: `feature/back/auth-api` (커밋 d66df93)

### 1. 인증 구조 설계 — 무엇을 정했나

**대상자와 사용자를 분리했다.** 서비스 대상이 독거노인뿐 아니라 1인 가구까지 넓어지면서,
"모니터링 대상"과 "앱을 쓰는 사람"이 같지 않은 경우가 생긴다.

| 경우 | 대상자 계정 | 앱 사용자 |
| --- | --- | --- |
| 독거 어르신 (다수) | 없음 (복지사가 대신 등록) | 자녀(보호자), 복지사 |
| 1인 가구 본인 | 있음 (SELF 관계) | 본인 + 비상연락 보호자 |

그래서 역할을 계정에 박지 않고 **가구와의 관계(멤버십)로 모델링**했다.
한 사람이 *내 가구는 SELF, 어머니 가구는 GUARDIAN*처럼 여러 역할을 동시에 가질 수 있다.

**인증번호는 로그인 수단이 아니라 "가구 접근 신청권"으로 결정했다.**
가구마다 고정된 공용 코드로 로그인하면
① 누가 확인했는지 감사 추적이 불가능하고
② 코드가 공유되면 개인 단위 차단이 안 되며
③ 보호자가 여럿일 때 알림 수신자·응답자를 구분할 수 없다.
어르신 생활 패턴이라는 민감 데이터에는 치명적이라, **정상 가입한 계정이 코드를 사용해야
멤버십이 생기는 방식**으로 구현했다.

### 2. 구현 내용

| 영역 | 내용 |
| --- | --- |
| 스키마(V5) | `user_profiles`(Keycloak 1:1 프로필), `household_guardians` → `household_members` 일반화(관계 SELF/GUARDIAN/STAFF + 알림 순서 분리), `household_invites` |
| Keycloak 연동 | `nilm-backend` 클라이언트(서비스 계정 + 비밀번호 그랜트) 추가, 사용자 생성·삭제·토큰 발급 대행 |
| 인증 API | `POST /api/auth/signup\|login\|refresh`, `GET /api/auth/me` |
| 멤버십 API | `/api/devices/households/{id}/members` 목록·수정·해제 |
| 초대 API | 발급(기본 72시간·1회용·역할 내장)·수락·목록·회수 |
| 게이트웨이 | `/api/auth/**` 라우트 추가, 가입·로그인·갱신만 permitAll |

설계 원칙 두 가지를 지켰다.
- **비밀번호는 저장하지 않는다** — Keycloak으로 통과만 시키고, 프로필 저장이 실패하면
  생성된 Keycloak 계정을 보상 삭제한다.
- **신원은 Keycloak, 관계는 우리 DB** — 이름·이메일을 중복 저장하지 않고 `keycloak_user_id`만 참조한다.
  예외는 알림 연락처인데, 알림 발송이 우리 서비스 기능이므로 우리가 소유한다.

### 3. E2E 검증 (실제 Keycloak + PostgreSQL) — 16/16 통과

복지사 가입 → PENDING(승인 대기) / 보호자 가입 → ACTIVE / 중복 이메일 409 /
로그인 토큰 발급 / 비밀번호 오류 400 / 가구 등록 시 등록자 자동 멤버 연결 /
미연결 사용자 가구 조회 403 / 초대 발급 → 수락 → **재사용 차단** → **회수 후 사용 차단** /
멤버 목록 알림 순서(PRIMARY 우선) 정렬 확인

## 트러블슈팅

- **로그인 실패(`Account is not fully set up`)**: Keycloak 기본 사용자 프로필이 성·이름을
  모두 필수로 요구하는데 firstName만 채워서 발생. lastName 자리를 채워 해결하고 사유를 코드 주석에 남김
- **Flyway 검증 실패**: 로컬 device_db에 미병합 브랜치(V4)가 적용돼 있어 충돌 → DB 재생성으로 처음부터 검증
- **마이그레이션 번호 주의**: 이 브랜치는 V5, 미병합 `mqtt-credential-lifecycle` 브랜치가 V4.
  **V4를 먼저 병합하거나, 이 브랜치가 먼저 병합되면 V4를 V6으로 재번호**해야 Flyway 순서 오류가 없다
