## 요약

`realtime-analysis-service`의 빠른 MVP 범위를 다시 정리하고 Python 기반 Kafka Consumer
서비스를 구현했다. 이번 MVP는 실제 AI 모델과 DB 연동보다 Kafka 입출력과 이상 감지 흐름을
먼저 검증하는 것을 목표로 했다.

Kafka의 `power.raw.v1`에서 전력 데이터를 받아 가구별 입력 버퍼를 구성하고,
`FakePredictor`가 반환한 가전 6종의 ON/OFF 결과를 임시 기준선과 비교한다. 평소 사용 마감
시각까지 가전 사용이 감지되지 않고 이상 점수가 임계치 이상이면, 팀에서 합의한 5개 필드
형식으로 `analysis.event.v1` 이벤트를 발행한다.

로컬 Docker Kafka 환경에서 입력 메시지 수신부터 이상 이벤트 발행까지 확인했다.

## 오늘 확정한 MVP 범위

### 구현 범위

```text
Kafka power.raw.v1
  → 입력 메시지 검증
  → 가구별 최근 299개 입력 버퍼
  → FakePredictor 가전 6종 ON/OFF 출력
  → 당일 가전 사용 상태 기록
  → JSON baseline과 비교
  → 이상 점수 및 임계치 확인
  → Kafka analysis.event.v1 발행
```

잘못된 입력은 `dlq.analysis`로 발행하고, 정상 처리 또는 DLQ 전송이 끝난 뒤에만
Kafka 입력 Offset을 수동으로 커밋하도록 했다.

### 이번 MVP에서 제외한 범위

- 실제 AI 모델 파일 로딩 및 추론
- `analysis_db` 연동
- 기준선 자동 계산 및 갱신
- 가전 사용 세션과 일일 활동 결과 영속화
- HTTP API 및 FastAPI
- Flink 기반 스트림 처리
- 재시작 후 버퍼와 일일 상태 복구
- 여러 이상 감지 알고리즘을 동시에 운용하는 정책 엔진

## Kafka 입력 계약 확인

AI 모델 입력에 필요한 특징은 다음 네 가지다.

1. `active_power`: 유효전력
2. `reactive_power`: 무효전력
3. `power_factor`: 역률
4. `current`: 전류

현재 확인한 Kafka 메시지 예시는 다음과 같다.

```json
{
  "message_id": "8f3b2a19-4d6e-4c72-9b12-a1b2c3d4e5f6",
  "household_id": "H001",
  "device_id": "main",
  "measured_at": "2026-09-08T03:41:05.120Z",
  "active_power": 1789.47,
  "reactive_power": 340.01,
  "power_factor": 0.982,
  "current": 8.279,
  "house": "H001",
  "device": "main",
  "ts": "2026-09-08T03:41:05.120Z",
  "power_w": 1789.47,
  "voltage": 220.0,
  "apparent_power": 1821.49
}
```

분석 서비스에서는 `message_id`, `household_id`, `device_id`, `measured_at`과 모델 입력
4개 필드를 표준 필드로 사용한다. `house`, `device`, `ts`, `power_w` 등의 기존 호환 필드와
현재 모델에서 사용하지 않는 부가 필드는 입력을 거부하지 않고 무시한다.

## Kafka 이상 이벤트 계약

팀에서 합의한 MVP 이벤트는 다음 5개 필드로 구성한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `event_id` | UUID | 이상 이벤트 고유 ID |
| `household_id` | VARCHAR | 이상이 감지된 가구 ID |
| `score` | INTEGER | 0~100 범위 이상 점수 |
| `occurred_at` | TIMESTAMP | 이상 감지 시각 |
| `reason` | JSON | 알고리즘별 판단 근거 |

`reason`은 고정 문자열이 아니라 알고리즘별 세부 근거를 담는 JSON 객체로 사용한다.

```json
{
  "event_id": "59aa1d98-f40b-44f7-8388-bec0cd002288",
  "household_id": "H001",
  "score": 86,
  "occurred_at": "2026-09-08T03:41:07.120Z",
  "reason": {
    "expected_until": "08:10",
    "normal_days": 12,
    "window_days": 14
  }
}
```

- 출력 토픽: `analysis.event.v1`
- Kafka Record Key: `household_id`
- 잘못된 입력 토픽: `dlq.analysis`

## FakePredictor 설계

실제 AI 모델이 준비되기 전에도 Kafka 입출력과 이상 감지 흐름을 검증할 수 있도록
`FakePredictor`를 구현했다.

출력 대상은 다음 6종으로 고정했다.

```text
KETTLE
INDUCTION
IRON
MICROWAVE
HAIR_DRYER
VACUUM_CLEANER
```

환경변수 `FAKE_ON_APPLIANCES`에 가전을 지정하면 해당 가전만 ON으로 반환한다.

```env
FAKE_ON_APPLIANCES=MICROWAVE,HAIR_DRYER
```

빈 값이면 모든 가전을 OFF로 반환한다.

```env
FAKE_ON_APPLIANCES=
```

향후 실제 모델을 붙일 때는 `predict()` 인터페이스와 6종 출력 순서를 유지하고
`FakePredictor`만 실제 구현체로 교체한다.

## MVP 기준선과 이상 판단

현재 기준선은 DB 대신 `config/baselines.json`에 저장한다.

```json
{
  "id": "226dfc19-3222-49a4-8fde-a314573aa23e",
  "household_id": "H001",
  "appliance_type": "MICROWAVE",
  "baseline_type": "ROUTINE_MISSED",
  "expected_until": "08:10",
  "normal_days": 12,
  "window_days": 14,
  "reliability_weight": 1.0,
  "enabled": true
}
```

의미는 다음과 같다.

```text
H001 가구가 최근 14일 중 12일 동안 전자레인지를 사용했으며,
평소 사용이 확인되어야 하는 마감 시각은 한국 시간 08:10이다.
```

점수 계산식은 다음과 같다.

```text
score = normal_days / window_days × 100 × reliability_weight
```

현재 예시에서는 다음과 같이 86점이 된다.

```text
12 / 14 × 100 × 1.0 = 85.71 → 86점
```

마감 시각 이후에도 해당 날짜의 가전 ON 기록이 없고, 86점이 설정 임계치 80점 이상이면
`ROUTINE_MISSED` 이상 이벤트를 만든다. 같은 날짜·가구·가전·기준선 유형의 이벤트는
메모리 상태를 이용해 한 번만 발행한다.

현재는 단순 사용 여부만 메모리에 저장한다. 향후에는 최초 사용 시각을 저장해 마감 이후의
늦은 사용과 마감 이전의 정상 사용을 더 정확히 구분해야 한다.

## Kafka 처리 안정성

Kafka Consumer의 자동 커밋을 비활성화했다.

```text
enable.auto.commit = false
```

처리 결과에 따른 커밋 기준은 다음과 같다.

| 처리 결과 | Offset 처리 |
| --- | --- |
| 정상 입력 및 분석 완료 | 수동 커밋 |
| 잘못된 JSON을 DLQ에 정상 발행 | 수동 커밋 |
| 입력 스키마 오류를 DLQ에 정상 발행 | 수동 커밋 |
| 이상 이벤트 발행 실패 | 커밋하지 않음 |
| Handler 내부 처리 실패 | 커밋하지 않음 |

Producer의 `flush()`는 다른 Consumer가 이벤트를 처리했는지를 확인하는 기능이 아니다.
현재 Producer가 Kafka 브로커에 이벤트를 전달했는지 기다리는 역할만 한다.

## 단위 테스트 결과

Kafka 없이 실행 가능한 단위 테스트를 작성했으며 총 11개 테스트가 통과했다.

```text
11 passed
```

주요 검증 항목은 다음과 같다.

- 입력 계약에 맞는 전력 메시지 검증
- 기존 호환 필드 무시
- 필수 모델 입력 누락 거부
- Kafka 토픽 기본 설정 확인
- Fake Predictor ON 가전 설정 파싱
- 마감 이후 루틴 누락 감지
- 사용한 가전은 루틴 누락에서 제외
- 같은 날짜의 동일 이벤트 중복 발행 방지
- 버퍼가 채워진 후 이상 이벤트 발행
- 정상 메시지 처리 후 Offset 커밋
- Handler 실패 시 Offset 미커밋

## 로컬 Docker 통합 검증

기존 `infrastructure/local/compose.yaml`은 수정하지 않았다. 실행 중인 로컬 Kafka 네트워크에
분석 서비스 컨테이너를 별도로 연결해 테스트했다.

빠른 확인을 위해 테스트 실행에서는 다음 설정을 사용했다.

```text
MODEL_WINDOW_SIZE=3
FAKE_ON_APPLIANCES=
ANALYSIS_SCORE_THRESHOLD=80
ANALYSIS_TIMEZONE=Asia/Seoul
```

Kafka UI에서 확인한 결과는 다음과 같다.

- Kafka 클러스터 `nilm-local`: Online
- `power.raw.v1`: 24 partitions, 메시지 6개 확인
- `analysis.event.v1`: 12 partitions, 메시지 2개 확인
- Consumer Group `realtime-analysis-mvp-test-1`: `STABLE`
- 분석 서비스가 Kafka Key `H001`로 86점 이벤트를 정상 발행

실제로 확인한 분석 서비스 출력은 다음과 같다.

```json
{
  "event_id": "f46567d2-2b29-486f-9051-8cae3ff28d6a",
  "household_id": "H001",
  "score": 86,
  "occurred_at": "2026-09-08T03:41:06.120000Z",
  "reason": {
    "expected_until": "08:10",
    "normal_days": 12,
    "window_days": 14
  }
}
```

이를 통해 다음 흐름을 확인했다.

```text
power.raw.v1 메시지 수신
  → 입력 검증
  → 테스트용 3개 버퍼 완성
  → FakePredictor 실행
  → baseline 조회 및 86점 계산
  → analysis.event.v1 발행 성공
```

## 테스트 중 발생한 문제

### 1. MQTT Bridge 인증 실패

초기에는 MQTT Bridge 로그에 다음 오류가 반복됐다.

```text
MQTT authentication/connection failed: Not authorized
```

Mosquitto의 `passwd`에 등록된 사용자와 `infrastructure/local/.env`의 인증 정보가 맞지 않아
발생한 문제였다. MQTT 인증 정보를 일치시켜 해결했다.

Bridge는 성공적으로 메시지를 전달할 때마다 로그를 출력하지 않는다. 인증과 구독,
Kafka 연결이 모두 준비되면 컨테이너 내부의 `/tmp/bridge-ready` 파일이 생성되도록 되어 있다.

### 2. 이상 이벤트 전송 대기시간 초과

첫 통합 테스트에서는 이상 이벤트 객체 생성까지 성공했지만 다음 오류가 발생했다.

```text
RuntimeError: 1 analysis events were not delivered
```

이 오류는 `flush(timeout=5)` 안에 Kafka 전달 완료를 확인하지 못해 발생했다. 이벤트 발행에
실패한 경우 원본 입력 Offset을 커밋하지 않고 Consumer를 종료하는 동작은 의도한 안전장치다.

이후 재시험에서는 분석 서비스가 생성한 이벤트가 `analysis.event.v1`에 정상 발행된 것을
확인했다. 다만 로컬 초기 연결 지연에 대비해 Producer timeout과 로그를 보강할 필요가 있다.

## 현재 MVP 제약과 주의사항

- 입력 버퍼, 당일 가전 사용 기록, 중복 발행 기록은 메모리에만 존재한다.
- 서비스가 재시작되면 299개 버퍼를 다시 채워야 한다.
- 재시작하면 같은 날짜의 동일 이벤트가 다시 발행될 수 있다.
- 메시지가 계속 들어오지 않으면 `ROUTINE_MISSED` 검사도 실행되지 않는다.
- 현재 기준선의 `expected_until`은 `Asia/Seoul` 기준이다.
- 기준선의 `household_id`와 Kafka 입력의 `household_id`가 일치해야 한다.
- 현재 점수 공식과 80점 임계치는 MVP 검증용이며 최종 알고리즘이 아니다.
- 테스트에서 사용한 `MODEL_WINDOW_SIZE=3`은 실제 실행 전에 299로 되돌려야 한다.
