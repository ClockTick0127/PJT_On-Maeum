# 외출 이벤트 연동 전달·운영·테스트 가이드

작성일: 2026-09-19

작성자: 최보경

## 1. 문서 목적

모니터링 서비스에서 관리하는 외출 시작·종료 상태를 AI 분석 서비스에 전달하기 위한 Kafka 계약과 운영 설정, 검증 절차를 정리한다.

AI 분석 서비스는 외출 정보를 다음 패턴에만 사용한다.

| 패턴 | 외출 반영 방식 |
| --- | --- |
| `PROLONGED_INACTIVITY` | 외출 중 감지 보류, 귀가 후부터 수면시간을 제외한 6시간 재계산 |
| `ROUTINE_MISSED` | 예상 첫 사용 판단 구간과 외출 구간이 겹치면 해당 날짜·가전 판단 제외 |
| `PROLONGED_APPLIANCE_USE` | 외출 여부와 관계없이 기존대로 감지 |
| `ROUTINE_CHANGED` | 이번 연동에서 변경하지 않음 |

## 2. 서비스 간 책임

```text
[Monitoring]
외출 상태 변경 감지 및 원본 이벤트 발행
        |
        | monitoring.household-presence.v1
        v
[AI realtime-analysis-service]
계약 검증 -> 최신 상태 저장 -> 패턴 판단
        |
        | analysis.event.v1
        v
[Monitoring]
Incident 및 알림 처리
```

### 모니터링 서비스 책임

- 사용자 또는 시스템의 외출 상태가 실제로 변경된 시점에 이벤트를 발행한다.
- 같은 가구의 이벤트는 `household_id`를 Kafka Key로 사용한다.
- 재시도할 때는 새 ID를 만들지 않고 동일한 `event_id`를 사용한다.
- `occurred_at`에는 Kafka 발행 시각이 아니라 실제 외출 상태 변경 시각을 기록한다.
- 가구별로 `OUTING_STARTED`와 `OUTING_ENDED`의 순서를 보장한다.

### AI 분석 서비스 책임

- 이벤트 계약을 검증하고 가구별 현재 상태와 최근 외출 구간을 한 행에 저장한다.
- 중복 이벤트를 멱등하게 처리한다.
- 외출 상태를 두 패턴 계산에 반영한다.
- 분석 결과만 `analysis.event.v1`로 발행한다.

모니터링 DB 상태 변경과 Kafka 발행을 함께 보장해야 한다면 모니터링 서비스에 Transactional Outbox 적용을 권장한다.

## 3. Kafka 계약

### 기본 설정

| 항목 | 값 |
| --- | --- |
| Topic | `monitoring.household-presence.v1` |
| Message Key | `household_id` |
| Value Format | UTF-8 JSON |
| Consumer Group | `realtime-analysis-service-outing-v1` |
| 지원 이벤트 | `OUTING_STARTED`, `OUTING_ENDED` |
| 전달 보장 | At-least-once 수신을 전제로 AI에서 멱등 처리 |

### 외출 시작

```json
{
  "event_id": "5fd787c0-f20f-42b9-a404-7baf53af990a",
  "household_id": "H001",
  "event_type": "OUTING_STARTED",
  "occurred_at": "2026-09-19T07:30:00+09:00"
}
```

### 외출 종료

```json
{
  "event_id": "e6973b37-0ca4-4a53-8acf-4e78a8d54d4c",
  "household_id": "H001",
  "event_type": "OUTING_ENDED",
  "occurred_at": "2026-09-19T08:00:00+09:00"
}
```

### 필드 정의

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `event_id` | UUID | Y | 재시도와 중복 수신을 구분하는 이벤트 식별자 |
| `household_id` | String | Y | 대상 가구 ID |
| `event_type` | Enum | Y | `OUTING_STARTED` 또는 `OUTING_ENDED` |
| `occurred_at` | ISO 8601 DateTime | Y | 실제 상태 변경 시각. UTC 또는 offset 포함 필수 |

현재 계약에는 `schema_version`, `event_category`, `reason`, `episode_id`를 사용하지 않는다. 정의되지 않은 추가 필드도 보내지 않는다.

### 발행 규칙

1. 외출이 시작되는 상태 전환에서 `OUTING_STARTED`를 한 번 발행한다.
2. 귀가하는 상태 전환에서 `OUTING_ENDED`를 한 번 발행한다.
3. 상태가 유지되는 동안 같은 의미의 이벤트를 주기적으로 발행하지 않는다.
4. Kafka 발행 실패 재시도에는 최초 `event_id`와 payload를 그대로 사용한다.
5. 반드시 `household_id`를 Key로 사용하여 한 가구의 이벤트가 같은 파티션에서 순서대로 처리되게 한다.

## 4. AI Consumer 처리 규칙

| 상황 | AI 처리 | Offset |
| --- | --- | --- |
| 정상 계약이며 DB 저장 성공 | 단일 상태 행 반영 | 커밋 |
| 같은 `event_id` 재수신 | 중복으로 무시 | 커밋 |
| 마지막 반영 시각보다 오래된 이벤트 | 현재 상태를 되돌리지 않고 무시 | 커밋 |
| JSON 또는 계약 오류 | `dlq.analysis` 전송 | DLQ 성공 후 커밋 |
| DB 저장 실패 | 서비스 오류로 처리하여 재시도 가능하게 유지 | 커밋하지 않음 |

`OUTING_ENDED`만 단독으로 도착하면 귀가 시각은 저장되지만 대응하는 외출 시작 시각이
없어 구간 겹침을 판단할 수 없다. 따라서 모니터링 서비스는 시작 이벤트 누락 없이
순서를 보장해야 한다.

## 5. 저장 구조

### 단일 테이블: `household_outing_state`

```text
household_id       PK
is_outing          현재 외출 여부
outing_started_at  가장 최근 외출 시작 시각, 귀가 후에도 유지
last_returned_at   최근 귀가 시각
last_event_id      마지막 반영 이벤트 ID
last_event_at      마지막 반영 이벤트 발생 시각
updated_at         수정 시각
```

외출 관련 테이블은 이것 하나만 사용한다. 새 외출이 시작되면 `outing_started_at`을 새
시각으로 덮어쓰고, 귀가하면 같은 행의 `last_returned_at`을 갱신한다. 따라서 가장 최근
외출 한 건의 구간만 판단할 수 있으며 전체 외출 이력은 보관하지 않는다.

## 6. 패턴 적용 기준

### 6.1 `PROLONGED_INACTIVITY`

```text
현재 외출 중
  -> 감지 보류

귀가 완료
  -> 계산 시작 = max(last_activity_at, last_returned_at)
  -> 23:00~07:00 수면시간 제외
  -> 깨어 있는 시간의 미활동이 6시간이면 이벤트 발행
```

예시:

```text
마지막 활동       2026-09-19 10:00 KST
외출 시작         2026-09-19 17:00 KST
귀가              2026-09-19 22:00 KST
수면 제외         2026-09-19 23:00 ~ 2026-09-20 07:00 KST
이벤트 예상       2026-09-20 12:00 KST
```

외출 중인 17:00~22:00은 위험 미활동으로 누적하지 않는다. 귀가 후 22:00~23:00의 1시간과 다음 날 07:00~12:00의 5시간을 합산한다.

### 6.2 `ROUTINE_MISSED`

현재 구현은 가전별 로컬 날짜 `00:00~expected_until`을 예상 첫 사용 판단 구간으로
사용하고, 상태 테이블에 저장된 가장 최근 외출 구간과 비교한다.

```text
baseline expected_until = 08:10
외출 구간               = 07:30~08:00
두 구간 겹침             = true
결과                     = 해당 날짜의 해당 가전 ROUTINE_MISSED 판단 제외
```

한 가전의 판단만 제외하며, 예상 마감 시각이 다른 가전은 각각 독립적으로 계산한다. 현재 기준선에 `expected_from`이 없기 때문에 자정부터 마감 시각까지를 사용한다는 점은 운영 시 유의한다.

## 7. 운영 설정

### AI 서비스 환경변수

```dotenv
KAFKA_OUTING_EVENT_TOPIC=monitoring.household-presence.v1
KAFKA_OUTING_GROUP_ID=realtime-analysis-service-outing-v1
KAFKA_OUTING_AUTO_OFFSET_RESET=earliest
```

Compose의 `realtime-analysis-service.environment`에는 다음처럼 명시하는 것을 권장한다.

```yaml
KAFKA_OUTING_EVENT_TOPIC: ${KAFKA_OUTING_EVENT_TOPIC:-monitoring.household-presence.v1}
KAFKA_OUTING_GROUP_ID: ${KAFKA_OUTING_GROUP_ID:-realtime-analysis-service-outing-v1}
KAFKA_OUTING_AUTO_OFFSET_RESET: ${KAFKA_OUTING_AUTO_OFFSET_RESET:-earliest}
```

환경변수를 명시하지 않아도 AI 코드 기본값은 위 값과 같다. 다만 운영 환경에서 설정 출처를 명확하게 하기 위해 Compose와 `.env`에 선언하는 편이 좋다.

### 로컬 토픽 생성

`infrastructure/local`에서 실행한다.

```powershell
docker exec nilm-kafka /opt/kafka/bin/kafka-topics.sh `
  --bootstrap-server localhost:19092 `
  --create --if-not-exists `
  --topic monitoring.household-presence.v1 `
  --partitions 24 `
  --replication-factor 1
```

로컬 단일 브로커이므로 replication factor는 1이다. 운영 환경에서는 Kafka 클러스터 정책에 맞춰 별도로 정한다.

### DB Migration

서비스 시작 시 Alembic을 적용하고 최신 revision을 확인한다.

```powershell
docker exec nilm-postgres psql -U nilm_admin -d analysis_db `
  -c "SELECT version_num FROM alembic_version;"
```

기대값:

```text
20260919_09
```

이전 revision `20260919_08`을 이미 적용한 DB에서는 `20260919_09`가 최근 외출 시각을
`household_outing_state`로 보존한 후 임시로 존재했던 두 번째 테이블을 삭제한다.

### Readiness

AI readiness 검사는 외출 입력 토픽을 필수 토픽으로 확인한다. 토픽이 없거나 접근할 수 없으면 `/ready`가 정상 상태가 되지 않는다.

### 9.2 Consumer 및 DB 연동 확인

Kafka UI에서 Key를 `H001`로 지정하고 `OUTING_STARTED`, `OUTING_ENDED`를 차례대로 발행한다.

DB 상태 확인:

```powershell
docker exec nilm-postgres psql -U nilm_admin -d analysis_db -c "SELECT household_id, is_outing, outing_started_at, last_returned_at, last_event_id, last_event_at FROM household_outing_state ORDER BY household_id;"
```

기대 결과:

- 시작 이벤트 후 `is_outing = true`, `outing_started_at` 저장
- 종료 이벤트 후 `is_outing = false`, `outing_started_at` 유지, `last_returned_at` 저장
- 가구별 행은 한 건만 존재

### 9.3 `ROUTINE_MISSED` 시나리오

사전 조건:

- `H001 / MICROWAVE` 기준선의 `expected_until = 08:10`
- 해당 날짜 00:00~08:10 사이 전자레인지 세션 없음

입력:

```text
07:30 OUTING_STARTED
08:00 OUTING_ENDED
08:10 이후 원천 전력 샘플 입력
```

기대 결과:

- 외출 구간이 예상 첫 사용 판단 구간과 겹치므로 해당 날짜의 `H001 / MICROWAVE`에 대해 `ROUTINE_MISSED`가 발행되지 않는다.
- 판단 구간이 겹치지 않는 다른 가전은 기존 규칙대로 판단한다.

### 9.4 `PROLONGED_INACTIVITY` 시나리오

입력:

```text
마지막 가전 활동: 2026-09-19 10:00 KST
OUTING_STARTED:   2026-09-19 17:00 KST
외출 중 샘플:     2026-09-19 21:00 KST
OUTING_ENDED:     2026-09-19 22:00 KST
확인 시각 1:      2026-09-20 11:59 KST
확인 시각 2:      2026-09-20 12:00 KST
```

기대 결과:

- 외출 중에는 `PROLONGED_INACTIVITY` 미발행
- 11:59까지 미발행
- 12:00에 6시간의 깨어 있는 미활동을 충족하여 한 번 발행
- `occurred_at`은 `2026-09-20T03:00:00Z`와 동일한 시각
- `reason.inactivity_started_at`은 귀가 시각인 `2026-09-19T22:00:00+09:00`에 대응
- `reason.threshold_hours = 6.0`
- `reason.sleep_window = {"start": "23:00", "end": "07:00"}`

시뮬레이터가 가상 시각 또는 무대기 실행을 지원하지 않으면 위 미래 시각 입력을 연속 발행하여 빠르게 검증하도록 시나리오 기능을 추가해야 한다.

### 9.5 중복 및 오류 메시지

중복 검증:

1. 동일한 `event_id`와 payload를 두 번 발행한다.
2. 단일 상태 행이 한 번만 갱신되는지 확인한다.

계약 오류 검증:

1. UUID가 아닌 `event_id`, timezone 없는 `occurred_at`, 미지원 `event_type` 중 하나를 발행한다.
2. `dlq.analysis`에 메시지가 한 번 전달되는지 확인한다.
3. Consumer가 다음 정상 메시지를 계속 처리하는지 확인한다.

### 9.6 Consumer Lag 확인

```powershell
docker exec nilm-kafka /opt/kafka/bin/kafka-consumer-groups.sh `
  --bootstrap-server localhost:19092 `
  --describe `
  --group realtime-analysis-service-outing-v1
```

정상 처리 후 대상 파티션의 `LAG`가 0인지 확인한다.

## 11. 로컬 테스트 데이터 정리 시 주의

테스트 데이터 삭제는 검증용 가구 ID만 정확히 지정해서 수행한다. 운영 또는 공용 개발 DB에서는 전체 테이블 삭제를 수행하지 않는다.

예시:

```sql
DELETE FROM household_outing_state WHERE household_id = 'H001';
```
