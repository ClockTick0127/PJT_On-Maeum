### 2. 역할(Role) 기획 구체화 — 발표 준비 중 확정

- 역할의 차이 = "볼 수 있는 가구의 범위" 프레임 확립
  - USER(대상자): 본인 가구 1곳 — 이상 시 본인 확인 알림의 1차 수신자 (대시보드 상시 이용 아님)
  - GUARDIAN(보호자): 연결된 가구만 — 상태·이벤트 조회, 이벤트 확인
  - ADMIN(관리자): **복지시설·기관 담당자**로 재정의 — 담당 가구 전체 관제 ("시스템 전체 관리" 아님)
- 시스템 전체 관리 role은 불필요 결론 — 계정·역할 관리는 Keycloak 콘솔 담당, 필요 시 추가 비용 낮음
- 단계적 확인(escalation) 흐름 확정: 이상 감지 → 대상자 본인 확인 → 무응답 시 보호자 → 시설 담당자
  - USER 토큰이 필요한 이유: "괜찮아요" 응답은 인증된 본인만 가능해야 함
- 역할(JWT) = API 종류 결정, 가구 범위 필터링 = 서비스 로직(관계 데이터)의 2단 구조로 정리

### 3. AI 파트 현황 파악 (NILM PoC 총정리 읽음)

- 현재 상태: 서비스 MVP가 아닌 **NILM 기술 PoC** — 동일 가구 학습에서 수동 가전 사용 신호
  추출 검증 완료, cross-house·실제 부재 감지는 미검증 (외부 검수 2회로 과장 표현 철회됨)
- 백엔드에 영향 있는 것 3가지
  1. 모델 입력이 4특징(유효·무효전력, 역률, 전류) — 현재 payload(power_w 단독)와 불일치
     가능성 → 하드웨어 확정 시 `power.raw.v1` 스키마 확장(v2) 검토 필요 (ESP32·AI 3자 확인)
  2. AI 산출물 확정 단계에 "추론 API 입출력 명세" 포함 → Analysis Service 요구사항의 원천,
     명세 정의에 백엔드 참여 필요
  3. 알림 단위가 "수 시간 내"에서 일 단위(D-rule)로 후퇴 중 → Monitoring 알림 설계·발표 표현 주의

### 4. 이상 감지 알고리즘 방향 정리 (발표 피드백 1차 반영)

- 피드백 핵심: 이상 판단 기준의 구체성, 오탐 방지(외출·여행 구분), 예방 vs 조기 발견 분리,
  탐지 후 대응 절차, 평가 지표(오탐률·미탐률·탐지 시간)
- 두 트랙 분리
  - **예방(위험 사용)**: 인덕션 등 ON 지속시간 임계 규칙 — 실시간, 즉시 구현 가능
  - **조기 발견(활동 부재)**: 단계적 고도화
- 로드맵
  - v1: 일 단위 개인화 무사용 판정 (가구별 사용 확률 기반 베르누이형 D-rule) + 부재 등록
  - v2: 경과 시간 기반 위험 점수 — "마지막 수동 가전 사용 후 경과 시간 ÷ 그 가구의 평소 최대
    무활동 간격" 비율 + 보조 신호(조명 지속, 새벽 활동 등) 가감 → 단계별 escalation
  - v3(데이터 축적 후): Isolation Forest 등 다차원 보강
- NILM이 필요한 이유 정리: 총전력은 냉장고 등 자동 가전 때문에 빈집도 "활동 중"으로 보임 —
  NILM = 수동 가전만 걸러 "사람의 활동" 정의 (PoC 실측: 총량 규칙 0.81 vs NILM 0.93)
- 활동 지수(활동량) 검토: 경보 주 신호로는 부적합, **추세 감시(EWMA)·대시보드 시각화·
  프라이버시 보완**용 파생 지표로 채택 권장
- 백엔드 액션 아이템 도출 (Monitoring Service 백로그)
  - 부재 등록 API (외출·여행·입원 기간 감지 억제)
  - 알림 단계 상태 머신 (관심 → 본인 확인 → 보호자 → 시설)
  - 이벤트 스키마: 위험도 + 사람이 읽을 사유 + 근거 신호 (+ activity_index)
  - 서비스 지표 수집: 오탐률·미탐률·평균 탐지 시간
