# 실시간 분석 파이프라인 단계별 레이턴시 1차 측정

> 측정일: 2026-09-14  
> 작성자: 최보경 (BE-2)  
> 대상 서비스: `ai/realtime-analysis-service`  
> 원본 로그: `infrastructure/local/clean-inference-600.log`

---

## 1. 측정 목적

`realtime-analysis-service`가 Kafka 메시지 한 건을 처리하는 전체 시간과 내부 단계별 시간을
분리해 최초 기준선(Baseline)을 확보한다. 이번 측정은 단계별 타이머와 구조화 로그가 실제
Docker·Kafka·PostgreSQL 환경에서 정상적으로 동작하는지 확인하고, 다음 성능 개선에서 먼저
확인할 병목을 찾는 것을 목적으로 한다.

이번 결과는 실제 AI 모델과 110 msg/s 부하를 적용하기 전의 1차 측정이다.

## 2. 측정 조건

| 항목 | 값 |
| --- | --- |
| 실행 환경 | 로컬 Docker Compose |
| 입력 시나리오 | `routine_missed` |
| 가구 | `H001` 1가구 |
| 입력 주기 | 1Hz |
| 전송 횟수 | 600건 |
| 모델 Window | 299건 |
| Predictor | `FakePredictor` |
| 분석 로그 | 메시지별 `pipeline_timing` JSON 1줄 |
| 백분위 계산 | 정렬 후 Nearest-rank 방식 |

실행 명령은 다음과 같다.

```cmd
python simulator.py --scenario routine_missed --count 600 --quiet
```

추론이 실행된 로그만 다음 명령으로 저장했다.

```cmd
docker compose logs --no-log-prefix realtime-analysis-service | findstr inference > clean-inference-600.log
```

## 3. 데이터 검증

| 검증 항목 | 결과 |
| --- | ---: |
| 시뮬레이터 입력 | 600건 |
| Window 워밍업 | 최초 298건 |
| 추론 포함 로그 | 302건 |
| `processed` | 302건 |
| `failed` | 0건 |
| `dlq` | 0건 |
| 대상 가구 | H001 302건 |
| Kafka Offset 범위 | 6908 ~ 7209 |
| JSON 파싱 실패 | 0건 |

600건 중 최초 298건은 299개 Window를 채우는 워밍업 구간이다. 299번째 입력부터 추론을
수행하므로 추론 로그 302건은 예상값인 `600 - 298`과 일치한다.

Kafka Offset이 0부터 시작하지 않는 이유는 Kafka Topic의 과거 데이터는 삭제하지 않고
분석 서비스 컨테이너와 로그만 새로 생성했기 때문이다. 원본 로그에는 컨테이너 재생성 이후의
측정 결과만 포함돼 있다.

## 5. 최초 연결 이상치

추론 구간의 첫 메시지는 다음과 같이 1,968.214ms가 걸렸다.

| 구간 | 시간 |
| --- | ---: |
| 전체 처리 | 1,968.214ms |
| Snapshot Broker ACK | 961.115ms |
| Event Broker ACK | 990.006ms |
| 일일 관측 DB | 13.087ms |
| 나머지 구간 | 약 4ms |

`AnalysisSnapshotPublisher`와 `AnalysisEventPublisher`가 서로 다른 Kafka Producer를 사용하며,
각 Producer가 첫 `produce/flush` 시점에 Broker 연결을 초기화한 비용으로 판단된다. 동일 실행에서
두 번째 메시지부터 Snapshot ACK는 정상 범위로 안정됐다.

최초 연결 비용도 실제 운영에서 발생하는 값이므로 제거하지 않고 별도로 기록한다. 다만 정상
처리 성능의 p50/p95/p99를 해석할 때는 최초 1건을 분리한다.

## 7. 병목 판단

### 7.1 1순위: 일일 관측 DB 쓰기

안정 상태에서 `observation_db`는 평균 11.238ms, p95 20.189ms로 전체 처리시간에서 가장 큰
비중을 차지한다. 현재 입력 메시지마다 `household_observation_daily` 조회 및 갱신 Transaction을
수행하는 구조와 일치한다.

향후 검토할 개선 후보는 다음과 같다.

- 가구·날짜별 Sample Count를 메모리에서 누적한 뒤 주기적으로 Batch Flush
- 메시지마다 수행하는 조회와 Transaction 횟수 축소
- PostgreSQL Upsert와 Batch Update 비교
- 장애 시 누적값 유실 범위 및 Kafka Offset Commit 계약 함께 검증

### 7.2 2순위: 최초 Kafka Producer 연결

첫 Snapshot과 Event 발행에서 각각 약 1초가 발생했다. 서비스 시작 시 Producer 연결을
준비하거나 공용 Producer를 사용하는 방안을 검토한다. 개선 후에도 재시작 직후의 첫 Event가
지연되지 않는지 별도 Cold-start 지표로 유지한다.

### 7.3 FakePredictor 결과 해석 주의

FakePredictor 추론 p95는 0.092ms이므로 실제 TCN 모델 성능을 나타내지 않는다. 실제 모델을
연동한 뒤 동일한 299개 Window 조건에서 추론 시간을 다시 측정해야 한다.

## 8. 요구사항 대비 판단

| 요구사항 | 이번 측정 판단 |
| --- | --- |
| NFR-001: 110 msg/s를 10분 처리 | 미검증. 이번 입력은 1 msg/s |
| NFR-002: 주요 Event E2E p95 5초 이내 | 미검증. 분석 서비스 내부 처리만 측정 |
| NFR-007: 단계별 관측성 | 1차 충족. 메시지별 구조화 로그에서 확인 가능 |
| NFR-009: CPU·Memory | 미측정 |

안정 상태 내부 처리 p95는 26.047ms로 5초보다 짧지만 MQTT 입력부터 Monitoring DB와 SSE까지의
전체 E2E가 아니므로 NFR-002 충족으로 판정하지 않는다.

현재 Consumer가 메시지를 순차 처리하므로 안정 상태 p95만 단순 역산하면 약 38 msg/s다.
이는 실제 최대 처리량이 아니라 110 msg/s 부하 시험 전의 위험 신호로만 사용한다. 실제 처리량은
110 msg/s 입력을 10분간 주입하고 Consumer Lag이 증가하는지 확인해 판정해야 한다.

## 9. `sensor_to_log_ns` 제외 사유

이번 `routine_missed` 시나리오는 당일 오전 08:15부터 시작하는 가상 시각을 `measured_at`으로
사용했다. 실제 로그 수집 시각과 약 6시간 차이가 발생하므로 `sensor_to_log_ns`는 네트워크 또는
처리 레이턴시가 아니다.

다음 재측정에서는 시뮬레이터 시작 시각을 실제 현재 시각으로 맞춘다.

```cmd
python simulator.py --scenario routine_missed --start-time %TIME:~0,8% --count 600 --quiet
```

시뮬레이터와 분석 서비스가 다른 장비에서 실행될 경우에는 양쪽 장비의 NTP 동기화 상태도 함께
기록한다.

## 10. 다음 측정 계획

1. 실제 현재 시각을 사용해 Simulator → MQTT → Bridge → Kafka → Analysis의
   `sensor_to_log_ns`를 재측정한다.
2. 실제 TCN 모델을 연결해 전처리 및 추론 p50/p95/p99를 다시 측정한다.
3. 110 msg/s를 10분간 입력해 처리량, Consumer Lag, DLQ, CPU와 Memory를 측정한다.
4. 일일 관측 DB 쓰기 개선 전후를 동일 조건으로 비교한다.
5. Monitoring에 Kafka 수신, DB Commit, Outbox 및 SSE 완료 시각을 추가해 전체 E2E를 측정한다.
