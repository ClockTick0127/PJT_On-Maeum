## 오늘 작업 요약

`realtime-analysis-service`에서 확정된 가전 ON/OFF 상태를 `analysis_db`에 저장하는
Repository를 실제 처리 흐름에 연결하고, 가구별 최신 전력 측정값과 가전 상태를
`analysis.snapshot.v1`으로 발행하는 기능을 구현했다.

오늘 완료한 주요 범위는 다음과 같다.

```text
power.raw.v1
  → 가구별 299개 입력 버퍼
  → Predictor의 가전 6종 ON 확률
  → 가전별 threshold 적용
  → 연속 판정 및 히스테리시스로 최종 ON/OFF 확정
  → 가전 사용 세션과 일일 활동 DB 저장
  → analysis.snapshot.v1 실시간 상태 발행
  → 루틴 이상 조건 충족 시 analysis.event.v1 발행
```

## 가전 사용 세션 및 일일 활동 DB 저장

SQLAlchemy 기반 `SqlAlchemyApplianceActivityRepository`를 구현하고 실제
`MeasurementHandler`에 연결했다.

### OFF → ON

가전의 `TURNED_ON` 전이가 확정되면 다음 처리를 하나의 DB 트랜잭션으로 수행한다.

1. `household_observation_daily`를 가구와 날짜 기준으로 조회하고, 없으면 생성한다.
2. `household_activity_daily`를 일일 관측과 가전 기준으로 조회하고, 없으면 생성한다.
3. `appliance_usage_session`에 새로운 사용 세션을 생성한다.
4. 세션 생성에 성공한 경우 `household_activity_daily.event_count`를 1 증가시킨다.
5. 모든 처리가 성공하면 한 번에 COMMIT하고, 하나라도 실패하면 전체 ROLLBACK한다.

### ON 유지

가전이 확정 ON 상태를 유지하는 동안 열린 세션의 `max_probability`를 확인한다.
현재 확률이 기존 최대 확률보다 클 때만 `max_probability`와 `updated_at`을 갱신한다.
히스테리시스 구간에서 ON 상태가 유지되는 경우도 같은 로직을 적용한다.

### ON → OFF

가전의 `TURNED_OFF` 전이가 확정되면 해당 가구와 가전의 열린 세션을 찾아
`ended_at`과 `updated_at`을 갱신한다.

### 중복 및 동시 처리

- 동일한 시작 시각의 세션이 이미 있으면 중복 INSERT하지 않는다.
- 이미 열린 세션이 있으면 새 세션 대신 기존 세션의 최대 확률만 갱신한다.
- 열린 세션 조회에는 `FOR UPDATE`를 사용해 같은 행의 동시 갱신을 방지한다.
- 확률은 DB의 `NUMERIC(5, 4)` 형식에 맞게 소수점 넷째 자리로 변환한다.

### 실제 DB 확인

DBeaver에서 다음 세 테이블을 JOIN해 데이터 저장 결과를 확인했다.

- `household_observation_daily`
- `household_activity_daily`
- `appliance_usage_session`

`H001`의 `MICROWAVE` 사용에 대해 일일 관측 행, `event_count=1`, 세션 시작 시각과
확률 정보가 연결되어 저장되는 것을 확인했다.

현재 `household_observation_daily`는 세션의 부모 행을 만들기 위해 최초 생성 시
다음 임시값을 사용한다.

```text
observation_status = COLLECTING
sample_count = 0
expected_sample_count = 86400
coverage_ratio = 0
```

실제 `sample_count`, `coverage_ratio`, 최종 관측 상태 누적은 별도 작업으로 남아 있다.

## 실시간 Snapshot 계약 확정

프론트 또는 Monitoring 서비스가 가구의 최신 전력값과 현재 켜진 가전을 확인할 수 있도록
다음 계약을 확정했다.

| 항목 | 값 |
| --- | --- |
| Kafka Topic | `analysis.snapshot.v1` |
| Kafka Record Key | `household_id` |
| Value | UTF-8 JSON Object |
| 발행 주기 | 입력 윈도우 완성 후 매 추론 시점 |

기본 설정이 `MODEL_WINDOW_SIZE=299`, 입력이 가구별 1Hz이면 최초 299개 샘플이
쌓인 이후부터 약 1초마다 Snapshot을 발행한다.

### Snapshot 계약

```json
{
  "schema_version": 1,
  "snapshot_id": "8f3b2a19-d6e-4c72-9b12-a1b2c3d4e5f6",
  "household_id": "H001",
  "observed_at": "2026-09-10T00:10:00Z",
  "published_at": "2026-09-10T00:10:00.125Z",
  "measurement": {
    "active_power": 1789.47,
    "reactive_power": 340.01,
    "power_factor": 0.982,
    "current": 8.279
  },
  "appliances": [
    {"appliance_type": "KETTLE", "is_on": false},
    {"appliance_type": "INDUCTION", "is_on": false},
    {"appliance_type": "IRON", "is_on": false},
    {"appliance_type": "MICROWAVE", "is_on": true},
    {"appliance_type": "HAIR_DRYER", "is_on": false},
    {"appliance_type": "VACUUM_CLEANER", "is_on": false}
  ]
}
```

### 시각 필드 구분

- `observed_at`: 전력 데이터가 실제 측정된 시각으로, 원본의 `measured_at`을 사용한다.
- `published_at`: 모델 추론과 상태 판정 후 Snapshot을 Kafka에 발행한 시각이다.

두 시각의 차이를 이용하면 측정부터 Snapshot 발행까지의 처리 지연을 확인할 수 있다.

### 가전 상태 기준

Snapshot의 `is_on`에는 모델 확률을 threshold와 한 번 비교한 순간 상태를 넣지 않는다.
연속 판정과 히스테리시스를 모두 통과한 최종 확정 상태를 사용한다.

```text
모델 확률
  → threshold 1차 판정
  → 연속 샘플 확인
  → 히스테리시스 적용
  → 최종 is_on
```

Snapshot에는 확률을 포함하지 않고 6개 가전의 최종 `is_on`만 제공한다.
이상 이벤트는 별도 `analysis.event.v1`으로 발행하므로 Snapshot과 역할을 분리했다.

## Snapshot 구현 내용

### 스키마와 변환

- `SnapshotMeasurement`: 유효전력, 무효전력, 역률, 전류 검증
- `SnapshotApplianceState`: 가전 코드와 최종 ON/OFF 상태
- `AnalysisSnapshot`: 전체 `analysis.snapshot.v1` 계약 검증
- 계약에 정한 6개 가전의 개수, 종류와 순서를 검증
- `snapshot_id`는 원본 입력의 `message_id`를 사용해 재처리 시에도 같은 ID 유지
- `observed_at`과 `published_at`을 UTC로 발행

### Kafka Publisher

- `AnalysisSnapshotPublisher` 구현
- `household_id`를 Kafka Key로 사용해 같은 가구의 메시지 순서 유지
- Snapshot을 UTF-8 JSON으로 직렬화
- Producer 전송 결과를 확인하고 실패하면 예외 발생
- 발행에 실패한 경우 Handler 처리가 실패하므로 입력 Kafka Offset을 커밋하지 않음

### 실행 환경

- 분석 서비스 설정에 `KAFKA_ANALYSIS_SNAPSHOT_TOPIC` 추가
- 로컬 Compose의 `kafka-init`에서 `analysis.snapshot.v1` 자동 생성
- EC2-A 분석 서비스 환경변수 추가
- EC2-B Kafka 토픽 초기화 설정 추가
- `.env.example` 파일에 기본 토픽명 추가
- 분석 서비스 README에 Snapshot 연동 계약 추가
