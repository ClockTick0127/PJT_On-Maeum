# Realtime Analysis Service MVP 요구사항 명세서

> 작성일: 2026-09-08  
> 담당: BE-2  
> 대상 서비스: `ai/realtime-analysis-service`  
> 관련 DB: PostgreSQL `analysis_db`  
> 상위 범위: NILM 아키텍처 A안 실시간 분석 MVP

## 1. 문서 목적

이 문서는 `realtime-analysis-service`가 MVP에서 제공해야 하는 기능, 데이터 입출력,
처리 규칙, 품질 기준과 제외 범위를 정의한다.

초기 MVP에서는 Flink를 사용하지 않는다. Python 기반 Kafka Consumer 서비스가 실시간 전력 데이터를 읽고,
AI 모델로 6종 가전의 사용 상태를 추론한 뒤 일일 활동과 이상 감지 결과를 생성한다.

---

## 2. 서비스 목표

분전반에서 측정한 가구 총전력 데이터로부터 대상 가전 6종의 사용 여부를 추론하고,
가구의 평소 활동 기준과 비교할 수 있는 일일·시간대별 활동 데이터를 생성한다.

### 대상 가전

1. 전기포트 `KETTLE`
2. 인덕션 `INDUCTION`
3. 전기다리미 `IRON`
4. 전자레인지 `MICROWAVE`
5. 헤어드라이기 `HAIR_DRYER`
6. 진공청소기 `VACUUM_CLEANER`

### 서비스가 제공하는 결과

- 가전별 ON/OFF 판정
- 가전 사용 세션의 시작·종료 시각
- 가전별 일일 사용 횟수
- 가구별 일일 데이터 수집 품질
- 가구별 평소 사용 빈도와 시간대 기준선
- 연속 활동 미감지 등 정책 기반 분석 이벤트

## 3. MVP 시스템 구성

```text
센서
  → MQTT
  → MQTT-Kafka Bridge
  → Kafka power.raw.v1
  → realtime-analysis-service (Python)
      ├─ 입력 검증·중복 제거
      ├─ 1Hz 정규화
      ├─ 가구별 최근 299초 버퍼
      ├─ AI 모델 추론
      ├─ 가전 사용 세션 생성
      ├─ 일일 활동 집계
      └─ 이상 감지 정책 적용
  → Kafka analysis.snapshot.v1 / analysis.event.v1
  → Monitoring Service
```

### 기술 방향

| 구분 | MVP 선택 |
| --- | --- |
| 언어 | Python |
| 스트림 입출력 | `confluent-kafka` Consumer/Producer |
| 모델 실행 | PyTorch 체크포인트 직접 로딩 |
| DB | PostgreSQL `analysis_db` |
| ORM·마이그레이션 | SQLAlchemy, Alembic |
| 상태 확인 | 경량 HTTP Health/Readiness 엔드포인트 |
| 향후 확장 | Redis 버퍼 또는 Flink State/Checkpoint |

## 4. 서비스 책임 범위

### 담당 범위

- Kafka 전력 데이터 소비
- 입력 데이터 검증 및 DLQ 처리
- 가구별 시계열 버퍼 관리
- AI 모델 로딩 및 추론
- 가전별 ON/OFF와 사용 세션 판정
- 일일 데이터 품질과 활동 결과 저장
- 일·시간대별 생활 기준선 생성에 필요한 데이터 제공
- 이상 감지 정책 적용
- 분석 Snapshot과 Event 발행
- Kafka Offset 관리 및 재시작 처리

### 담당하지 않는 범위

- AI 모델 학습과 성능 개선
- 원본 전력 데이터 장기 보관
- 사용자 로그인과 권한 관리
- 사용자용 조회 API 및 SSE
- Incident 영구 저장과 담당자 조치
- 문자·카카오 등 실제 알림 발송
- 실제 재실·부재 또는 위험 상태 확정
- Flink 기반 분산 처리

## 5. 기능 요구사항

### 5.1 Kafka 입력 처리

| ID | 요구사항 |
| --- | --- |
| FR-001 | 서비스는 Kafka `power.raw.v1` 토픽의 전력 데이터를 지속적으로 소비해야 한다. |
| FR-002 | Kafka 메시지 Key는 가구별 처리 순서를 유지할 수 있도록 `household_id`를 사용해야 한다. |
| FR-003 | 서비스는 필수 필드 누락, 타입 오류, 허용 범위를 벗어난 값과 잘못된 시각을 검증해야 한다. |
| FR-004 | 검증에 실패한 메시지는 원인과 원본 정보를 포함해 `dlq.analysis`로 발행해야 한다. |
| FR-005 | 동일한 원본 메시지가 재전달돼도 분석 결과와 사용 세션이 중복 생성되지 않아야 한다. |
| FR-006 | 늦게 도착하거나 순서가 뒤바뀐 데이터는 설정된 허용 범위 안에서 측정 시각 기준으로 정렬해야 한다. |

### 5.2 입력 정규화와 버퍼

| ID | 요구사항 |
| --- | --- |
| FR-007 | 모델 입력은 1Hz 기준의 시계열 데이터로 정규화해야 한다. |
| FR-008 | 서비스는 `household_id`별로 최근 299초의 모델 입력 데이터를 유지해야 한다. |
| FR-009 | 299초 데이터가 모두 준비되지 않은 가구는 `WARMING_UP` 상태로 처리하고 추론 결과를 확정하지 않아야 한다. |
| FR-010 | 입력 특징은 모델 manifest에 정의된 순서와 타입을 따라야 한다. |

### 5.3 AI 모델 로딩과 추론

| ID | 요구사항 |
| --- | --- |
| FR-011 | 서비스는 시작 시 `model_artifact`에서 `ACTIVE` 모델의 위치를 조회해야 한다. |
| FR-012 | 서비스는 `artifact_uri`에서 모델 파일과 manifest를 로딩해야 한다. |
| FR-013 | manifest에는 입력 주기, 윈도우 크기, 입력 특징, 출력 인덱스별 가전 종류와 threshold가 포함돼야 한다. |
| FR-014 | 모델은 한 번의 추론으로 대상 가전 6종의 사용 확률을 출력해야 한다. |
| FR-015 | 서비스는 가전별 출력 확률과 threshold를 비교해 ON/OFF 상태를 판정해야 한다. |
| FR-016 | 활성 모델이 없거나 모델 로딩에 실패하면 Readiness를 실패 상태로 표시하고 전력 메시지를 정상 처리한 것으로 커밋하지 않아야 한다. |

### 5.4 가전 사용 세션

| ID | 요구사항 |
| --- | --- |
| FR-017 | 가전 상태가 OFF에서 ON으로 변경되면 새로운 사용 세션을 시작해야 한다. |
| FR-018 | 가전 상태가 ON에서 OFF로 변경되면 진행 중인 사용 세션을 종료해야 한다. |
| FR-019 | 짧은 ON/OFF 반복은 가전별 병합 규칙에 따라 하나의 세션으로 합칠 수 있어야 한다. |
| FR-020 | 사용 세션에는 시작 시각, 종료 시각과 세션 중 최대 추론 확률을 저장해야 한다. |
| FR-021 | 세션 시작·종료 이벤트에는 중복 처리를 막을 수 있는 결정적 `event_id`가 포함돼야 한다. |

### 5.5 일일 관측 상태

| ID | 요구사항 |
| --- | --- |
| FR-022 | 서비스는 가구·날짜별 정상 처리 샘플 수를 `household_observation_daily`에 집계해야 한다. |
| FR-023 | 수집률은 `sample_count / expected_sample_count`로 계산해야 한다. |
| FR-024 | 예상 샘플 수는 계획된 관측 시간과 목표 샘플 주기를 기준으로 계산해야 한다. |
| FR-025 | 예기치 않은 센서 장애 시간은 예상 샘플 수에서 제외하지 않아야 한다. |
| FR-026 | 관측 상태는 `COLLECTING`, `VALID`, `INSUFFICIENT_DATA`, `SENSOR_GAP`, `PROCESSING_ERROR`, `EXCLUDED` 중 하나로 관리해야 한다. |
| FR-027 | `VALID`가 아닌 날짜는 실제 미사용일로 판단하거나 기준선 계산에 포함하지 않아야 한다. |

### 5.6 가전별 일일 활동

| ID | 요구사항 |
| --- | --- |
| FR-028 | 서비스는 관측 결과별 대상 가전 6종의 `household_activity_daily` 행을 관리해야 한다. |
| FR-029 | `event_count`는 해당 날짜와 가전에 연결된 완료된 사용 세션 수와 일치해야 한다. |
| FR-030 | 사용이 감지되지 않은 가전도 일일 마감 시 `event_count = 0`인 행을 가져야 한다. |
| FR-031 | 날짜 기준은 `Asia/Seoul`을 사용해야 한다. |
| FR-032 | 일일 마감 작업은 전날의 관측 상태와 가전별 활동 결과를 확정해야 한다. 정확한 실행 시각은 운영 설정으로 관리한다. |

### 5.7 시간대 분석

| ID | 요구사항 |
| --- | --- |
| FR-033 | 서비스는 `appliance_usage_session.started_at`과 `ended_at`을 이용해 시간대별 사용 횟수와 지속 시간을 계산할 수 있어야 한다. |
| FR-034 | MVP에서는 별도 시간별 집계 테이블을 만들지 않고 사용 세션을 시간 단위로 집계해야 한다. |
| FR-035 | 시간대별 사용확률과 선호 시간 구간은 `routine_baseline.baseline_data`에 저장할 수 있어야 한다. |
| FR-036 | PoC에서 확인된 시간대 편차를 고려해 시간대 이탈 하나만으로 높은 위험 이벤트를 생성하지 않아야 한다. |

### 5.8 기준선 생성과 갱신

| ID | 요구사항 |
| --- | --- |
| FR-037 | 기준선은 `VALID` 상태의 일일 활동 데이터만 사용해 계산해야 한다. |
| FR-038 | `daily_use_probability`는 `active_days / sample_days`로 계산해야 한다. |
| FR-039 | 기준선은 `household_id + appliance_type + baseline_type` 조합별 하나만 유지해야 한다. |
| FR-040 | 기준선 재계산 시 기존 행의 통계값과 `calculated_at`을 갱신해야 한다. |
| FR-041 | 최소 유효 관측일을 충족하지 않은 신규 가구는 `LEARNING` 상태로 취급하고 활동 미감지 이벤트를 생성하지 않아야 한다. |
| FR-042 | 기준선 계산 주기와 최소 유효 관측일은 설정값으로 관리해야 한다. |

### 5.9 이상 감지 정책

| ID | 요구사항 |
| --- | --- |
| FR-043 | 서비스는 활성화된 `analysis_policy`를 조회해 이상 감지에 적용해야 한다. |
| FR-044 | 이상 감지 알고리즘과 세부 조건은 `algorithm_type`과 `parameters`로 구분해야 한다. |
| FR-045 | 연속 활동 미감지 정책은 `VALID` 상태인 날짜만 연속 일수 계산에 사용해야 한다. |
| FR-046 | 정책 조건이 만족되면 정책에 지정된 `event_type`, `score`, `severity`를 포함한 이벤트를 생성해야 한다. |
| FR-047 | 같은 가구에서 같은 정책 이벤트가 반복될 경우 `cooldown_hours` 동안 재발행하지 않아야 한다. |
| FR-048 | 이후 신뢰 가능한 가전 활동이 감지되면 기존 이상 상황을 해소하는 이벤트를 생성할 수 있어야 한다. |

### 5.10 Kafka 출력

| ID | 요구사항 |
| --- | --- |
| FR-049 | 서비스는 가구의 최신 분석 상태를 `analysis.snapshot.v1`에 발행해야 한다. |
| FR-050 | 서비스는 가전 ON/OFF, 사용 세션과 이상 감지 결과를 `analysis.event.v1`에 발행해야 한다. |
| FR-051 | 출력 Kafka Key는 `household_id`를 사용해야 한다. |
| FR-052 | 출력 이벤트에는 `event_id`, `household_id`, `event_type`, `occurred_at`과 이벤트별 payload가 포함돼야 한다. |
| FR-053 | 이벤트 처리 성공 여부를 추적할 수 있도록 모델 버전과 정책 코드를 payload에 포함할 수 있어야 한다. |

### 5.11 재시작과 오류 처리

| ID | 요구사항 |
| --- | --- |
| FR-054 | 입력 Offset은 필요한 DB 저장과 Kafka 출력이 성공한 후 커밋해야 한다. |
| FR-055 | 재처리로 동일 메시지를 다시 소비해도 같은 사용 세션과 분석 이벤트가 중복 생성되지 않아야 한다. |
| FR-056 | 서비스 재시작 후 마지막으로 커밋된 Kafka Offset 이후부터 처리를 계속해야 한다. |
| FR-057 | 메모리 버퍼가 복구되지 않는 MVP에서는 재시작 후 최대 299초의 워밍업을 허용해야 한다. |
| FR-058 | DB 또는 출력 Kafka 장애 시 입력을 성공 처리한 것으로 커밋하지 않고 재시도해야 한다. |

## 6. 데이터 요구사항

### 6.1 `power.raw.v1` 입력 계약 초안

AI 모델의 실제 입력 계약은 AI 파트와 센서·Bridge 담당자의 확인 후 확정한다.

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `message_id` | UUID/String | Y | 중복 제거를 위한 원본 메시지 ID |
| `household_id` | String | Y | 가구 식별자 및 Kafka Key |
| `device_id` | String | Y | 측정 장치 식별자 |
| `measured_at` | ISO-8601 Timestamp | Y | 센서 측정 시각 |
| `active_power` | Number | Y | 유효전력 |
| `reactive_power` | Number | Y | 무효전력 |
| `power_factor` | Number | Y | 역률 |
| `current` | Number | Y | 전류 |

```json
{
  "message_id": "01JXYZ...",
  "household_id": "H001",
  "device_id": "main",
  "measured_at": "2026-09-08T09:00:00+09:00",
  "active_power": 1250.4,
  "reactive_power": 130.2,
  "power_factor": 0.92,
  "current": 5.8
}
```

### 6.2 `analysis.event.v1` 출력 계약 초안

```json
{
  "event_id": "01JABC...",
  "household_id": "H001",
  "event_type": "APPLIANCE_ON",
  "occurred_at": "2026-09-08T09:02:10+09:00",
  "score": 65,
  "severity": "WATCH",
  "correlation_key": "H001:MICROWAVE:20260908-001",
  "payload": {
    "appliance_type": "MICROWAVE",
    "probability": 0.87,
    "model_version": "v1.0.0"
  }
}
```

### 6.3 주요 DB 테이블

| 테이블 | 역할 |
| --- | --- |
| `model_artifact` | 현재 사용할 AI 모델의 이름, 버전과 파일 위치 관리 |
| `routine_baseline` | 가구·가전별 일 사용확률과 시간대 기준 관리 |
| `analysis_policy` | 이상 감지 알고리즘과 이벤트 생성 조건 관리 |
| `household_observation_daily` | 가구별 일일 데이터 수집 품질 관리 |
| `household_activity_daily` | 가전별 일일 사용 횟수 관리 |
| `appliance_usage_session` | 개별 가전 사용의 시작·종료 시각 관리 |

상세 ERD와 컬럼 설명은 `analysis_db_ERD_명세.md`를 따른다.

## 7. 외부 HTTP API 요구사항

MVP에서는 사용자 또는 다른 서비스가 호출하는 공개 도메인 API를 제공하지 않는다.
서비스 간 업무 데이터 교환은 Kafka로 수행한다.

상태 확인을 위한 내부 엔드포인트만 제공한다.

| Method | Path | 설명 |
| --- | --- | --- |
| GET | `/health` | 프로세스가 실행 중인지 확인 |
| GET | `/ready` | Kafka, DB, ACTIVE 모델이 준비돼 메시지를 처리할 수 있는지 확인 |

모델 등록·활성화, 기준선 수정과 정책 수정 API는 MVP 범위에서 제외하고 DB 초기 데이터 또는 운영 스크립트로 관리한다.

## 8. 비기능 요구사항

| ID | 분류 | 요구사항 |
| --- | --- | --- |
| NFR-001 | 처리량 | 110 msg/s 입력을 10분 동안 처리하고 Consumer Lag이 지속적으로 증가하지 않아야 한다. |
| NFR-002 | 지연 | 필요한 299초 입력이 준비된 이후 생성되는 주요 분석 이벤트는 발행까지 p95 5초 이내를 목표로 한다. |
| NFR-003 | 정확도 | 합의한 ON/OFF 30회 시나리오에서 80% 이상 판정을 목표로 하며 측정 방법을 함께 기록한다. |
| NFR-004 | 멱등성 | Kafka 재전달 또는 서비스 재시작으로 동일 세션과 이벤트가 중복 생성되지 않아야 한다. |
| NFR-005 | 복구 | 프로세스 재시작 후 마지막 커밋 Offset부터 처리를 재개해야 한다. |
| NFR-006 | 데이터 품질 | 센서 장애와 실제 가전 미사용을 구분해야 한다. |
| NFR-007 | 관측성 | Consumer Lag, 처리 건수, DLQ 건수, 추론 시간, 오류 건수와 모델 버전을 로그 또는 메트릭으로 확인할 수 있어야 한다. |
| NFR-008 | 보안 | Health/Readiness 외 포트를 외부에 공개하지 않고 DB·Kafka 접속 정보는 환경변수로 관리해야 한다. |
| NFR-009 | 자원 | 서비스 메모리와 CPU 사용량을 측정하고 EC2-B의 할당량 안에서 동작해야 한다. 정확한 상한은 배포 설정에서 확정한다. |

## 9. 업무 규칙

| ID | 규칙 |
| --- | --- |
| BR-001 | `observation_status != VALID`인 날짜는 가전 미사용일로 계산하지 않는다. |
| BR-002 | `household_activity_daily.event_count > 0`이면 해당 날짜에 그 가전을 사용한 것으로 본다. |
| BR-003 | `event_count`는 연결된 완료 세션 수와 일치해야 한다. |
| BR-004 | 가전별 사용 여부는 모델 출력 확률과 manifest의 가전별 threshold를 비교해 결정한다. |
| BR-005 | 기준선은 최소 유효 관측일을 충족한 가구에만 생성한다. |
| BR-006 | 시간대 패턴은 초기 MVP에서 보조 지표로 사용하고 단독 위험 확정 조건으로 사용하지 않는다. |
| BR-007 | AI 결과는 가전 활동의 대리지표이며 실제 부재나 위험 상태를 확정하지 않는다. |

## 10. 완료 기준

| 번호 | 완료 조건 |

| 1 | `power.raw.v1` 입력을 검증하고 정상·비정상 메시지를 각각 처리한다. |
| 2 | 가구별 299초 입력 버퍼가 구성되고 멀티라벨 모델 추론이 실행된다. |

| 4 | 일일 관측 상태와 가전별 `event_count`가 DB에 저장된다. |
| 5 | 개별 세션의 시작·종료 시각으로 시간대별 사용을 조회할 수 있다. |
| 6 | `VALID`가 아닌 날짜는 기준선과 연속 미사용 계산에서 제외된다. |
| 7 | 활성 정책 조건을 만족하면 `analysis.event.v1`에 이벤트가 발행된다. |
| 8 | 동일 입력을 재처리해도 세션과 이벤트가 중복 생성되지 않는다. |
| 9 | 서비스 재시작 후 Kafka 처리가 재개되고 워밍업 상태가 구분된다. |
| 10 | 110 msg/s 10분 테스트 결과와 Lag, 추론 지연, 오류 건수가 기록된다. |
