# 진행 상황 회고 — 2026.09.07

작성자: 최보경

## 요약

NILM 아키텍처 A안에서 BE-2가 담당할 실시간 분석 영역의 일주일 작업 범위를 검토하고,
기존 AI PoC 문서를 바탕으로 `realtime-analysis-service`의 초기 구현 방향과
`analysis_db` MVP ERD를 구체화했다.

초기 MVP에서는 Flink를 사용하지 않고 Python Kafka Consumer 형태로 시작한다.
AI 모델은 총전력의 299초 구간과 4개 전력 특징을 입력받아 6종 가전의 사용 확률을 동시에 출력하며,
이 결과를 일 단위 활동으로 집계한 뒤 연속 활동 미감지 규칙을 적용한다.

## 확인한 AI PoC 구조

### 모델의 목적

- 분전반 총전력에서 모든 부하를 완전히 분해하는 것이 아니라, 생활 활동의 대리지표가 될 수 있는
  수동 가전의 사용 이벤트를 분류한다.
- 대상 가전은 전기포트, 인덕션, 전기다리미, 전자레인지, 헤어드라이기, 진공청소기 6종이다.
- 공개데이터에는 실제 재실·부재 정답이 없으므로 AI 결과를 실제 부재 또는 위험 확정으로 표현하지 않는다.
- 현재 검증 범위는 가전 사용 감지와 가전 무사용 기반의 확인 후보 생성까지다.

### 모델 입력과 출력

- 입력 주기: 1Hz
- 입력 구간: 최근 299초
- 입력 특징: 유효전력, 무효전력, 역률, 전류
- 출력: 6종 가전별 사용 확률
- 후처리: 가전별 threshold를 적용해 ON/OFF 이벤트 생성

```text
센서 데이터
  → Kafka power.raw.v1
  → 1Hz 정규화 및 최근 299초 버퍼 구성
  → 전력 변화 후보 탐지
  → TCN 추론
  → 가전별 사용 확률 및 ON/OFF 판정
  → 일 단위 활동 집계
  → 연속 활동 미감지 규칙
  → analysis.snapshot.v1 / analysis.event.v1
```

### PoC에서 확인된 제약

- 시각 루틴의 편차가 커서 "매일 오전 7~9시 전기포트 사용" 같은 좁은 시간대 규칙을
  MVP의 핵심 이상 기준으로 사용하기 어렵다.
- 초기 이상 판단은 가전의 일 단위 사용 여부와 D일 연속 활동 미감지 방식이 적절하다.
- D=1/2/3 중 어떤 값을 사용할지는 아직 확정되지 않았다.
- 현재 리플레이 Producer의 `power_w` 단일 값만으로는 4개 특징을 요구하는 TCN을 실행할 수 없다.
  센서·Bridge·Kafka 입력 계약을 먼저 확정해야 한다.

## realtime-analysis-service 초기 역할

초기 MVP에서는 Flink 대신 Python 서비스로 구현한다.

### 기술 방향

- Python
- `confluent-kafka` 기반 Kafka Consumer/Producer
- PyTorch 모델 직접 로딩
- SQLAlchemy + PostgreSQL
- 필요 시 FastAPI로 내부 관리 API 제공

### 담당 책임

1. `power.raw.v1` 소비 및 입력 스키마 검증
2. 중복 데이터 제거와 시간 순서 보정
3. 가구별 최근 299초 입력 버퍼 관리
4. 전력 변화 후보 탐지 및 TCN 추론
5. 6종 가전별 사용 확률과 ON/OFF 이벤트 생성
6. 가구·가전별 일 단위 활동 집계
7. 생활 기준선 및 정책과 비교해 활동 미감지 이벤트 생성
8. `analysis.snapshot.v1`, `analysis.event.v1`, `dlq.analysis` 발행

### 담당하지 않는 책임

- AI 모델 학습
- 초 단위 원본 데이터 장기 보관
- 사용자용 조회 API와 SSE
- Incident 영구 저장 및 담당자 조치
- 실제 부재·위험 상태 확정

### 장애 복구에 대한 MVP 기준

- 최근 299초 버퍼는 서비스 메모리에 유지한다.
- 재시작 직후에는 버퍼가 채워질 때까지 약 299초의 워밍업을 허용한다.
- Kafka 출력 성공 후 입력 Offset을 커밋한다.
- 재처리 가능성에 대비해 이벤트 ID를 결정적으로 만들고 Monitoring에서 중복을 제거한다.
- 향후 Redis 버퍼 또는 Flink State/Checkpoint로 확장한다.

## analysis_db 저장 원칙

`analysis_db`에는 초 단위 원본 데이터나 모든 추론 확률을 계속 적재하지 않는다.
분석 서비스가 사용하는 모델 정보, 가구별 생활 기준선, 이상 판단 정책과 일 단위 집계 결과를 저장한다.

```text
원본 전력 데이터       → Kafka / S3
실시간 이벤트          → Kafka / monitoring_db
299초 추론 버퍼         → 서비스 메모리
모델·기준선·정책·집계값 → analysis_db
```

## MVP ERD 결정안

### 1. model_artifact

하나의 멀티라벨 모델이 6종 가전을 동시에 출력하므로 모델 테이블에 `appliance_type`을 두지 않는다.
가전 출력 순서, 가전별 threshold, 입력 특징과 성능 지표는 모델 파일과 함께 배포하는
`manifest.json`에서 관리한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | UUID | 모델 ID |
| `model_name` | VARCHAR(100) | 모델 이름 |
| `version` | VARCHAR(50) | 모델 버전 |
| `artifact_uri` | VARCHAR(500) | 모델 파일 및 manifest 위치 |
| `status` | VARCHAR(20) | `VALIDATED`, `ACTIVE`, `RETIRED` |
| `created_at` | TIMESTAMP | 모델 등록 시각 |

- 같은 `model_name + version`은 중복 등록하지 않는다.
- 이번 MVP에서 모델을 서비스에 고정 배포한다면 이 테이블 자체를 제외할 수도 있다.
- 모델 동적 선택이 필요할 때만 DB에 유지한다.
- 모델 파일 무결성 검증이 필요해지면 추후 `checksum`을 추가한다.

### 2. routine_baseline

가구별·가전별 평소 사용 빈도를 저장한다. MVP에서는 최근 관측일 중 해당 가전이 사용된 날짜의
비율을 기준선으로 사용한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | UUID | 기준선 ID |
| `household_id` | VARCHAR(50) | 가구 ID |
| `appliance_type` | VARCHAR(50) | 가전 종류 |
| `baseline_type` | VARCHAR(30) | 기준선 계산 방식, MVP는 `DAILY_USAGE_RATE` |
| `sample_days` | SMALLINT | 정상적으로 관측한 일수 |
| `active_days` | SMALLINT | 가전 사용이 감지된 일수 |
| `daily_use_probability` | DECIMAL(5,4) | `active_days / sample_days` |
| `reliability_weight` | DECIMAL(5,4) | 활동 판단에 반영할 신뢰 가중치 |
| `enabled` | BOOLEAN | 활동 판단 사용 여부 |
| `calculated_at` | TIMESTAMP | 마지막 계산 시각 |

- 가구·가전·기준선 종류 조합은 하나만 유지하고 재계산 시 갱신한다.
- 기준선은 새 가구의 초기 학습 기간 동안 생성하지 않고 `LEARNING` 상태로 둬야 한다.
- PoC 기준 최초 20일의 유효 활동 기록으로 생성하고, 이후 주 1회 재계산하는 방향을 검토했다.
- 센서 장애일과 분석 실패일은 `sample_days`에서 제외해야 한다.
- `reliability_weight` 계산식은 아직 최종 확정하지 않았다. 후보식은
  `일 사용확률 × 모델 precision × 관측일 충족도`다.

### 3. analysis_policy

일 단위 활동 결과를 어떤 알고리즘으로 해석하고 어떤 이벤트를 생성할지 저장한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | UUID | 정책 ID |
| `policy_code` | VARCHAR(50) | 정책 식별자 |
| `algorithm_type` | VARCHAR(50) | 이상 판단 방식 |
| `parameters` | JSONB | 알고리즘별 세부 설정 |
| `event_type` | VARCHAR(50) | 조건 만족 시 생성할 이벤트 |
| `score` | SMALLINT | 이벤트 점수 |
| `severity` | VARCHAR(20) | 이벤트 심각도 |
| `cooldown_hours` | SMALLINT | 동일 이벤트 반복 방지 시간 |
| `enabled` | BOOLEAN | 정책 활성 여부 |
| `created_at` | TIMESTAMP | 정책 등록 시각 |

MVP 정책 예시:

```json
{
  "policy_code": "DAILY_ACTIVITY_MISSING",
  "algorithm_type": "CONSECUTIVE_INACTIVITY",
  "parameters": {
    "consecutive_inactive_days": 2,
    "minimum_reliable_appliances": 2,
    "minimum_reliability_weight": 0.5
  },
  "event_type": "ROUTINE_MISSED",
  "score": 80,
  "severity": "CONFIRM",
  "cooldown_hours": 48
}
```

- MVP에서는 정책 버전과 예약 적용 기간(`version`, `effective_from`, `effective_to`)을 제외한다.
- 알고리즘에 따라 달라지는 값은 `parameters` JSONB에 저장해 스키마 변경을 줄인다.

### 4. household_observation_daily

가구 단위로 하루 동안 센서 데이터가 정상적으로 들어왔는지 저장한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | UUID | 일일 관측 ID |
| `household_id` | VARCHAR(50) | 가구 ID |
| `observation_date` | DATE | 관측 날짜 |
| `sample_count` | BIGINT | 정상 수신한 1Hz 샘플 수 |
| `expected_sample_count` | BIGINT | 예상 샘플 수 |
| `coverage_ratio` | DECIMAL(5,4) | 정상 수집 비율 |
| `observation_status` | VARCHAR(30) | 수집 상태 |
| `is_finalized` | BOOLEAN | 일일 집계 완료 여부 |
| `finalized_at` | TIMESTAMP | 집계 완료 시각 |
| `created_at` | TIMESTAMP | 생성 시각 |
| `updated_at` | TIMESTAMP | 수정 시각 |

관측 상태 후보:

```text
COLLECTING
VALID
SENSOR_GAP
INSUFFICIENT_DATA
PROCESSING_ERROR
EXCLUDED
```

### 5. household_activity_daily

정상적으로 수집된 하루의 데이터를 AI가 가전별로 분석한 결과를 저장한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | UUID | 가전별 일일 활동 ID |
| `observation_daily_id` | UUID | `household_observation_daily` 참조 |
| `appliance_type` | VARCHAR(50) | 대상 가전 |
| `activity_detected` | BOOLEAN | 해당 날짜 사용 감지 여부 |
| `event_count` | INTEGER | 감지된 사용 이벤트 수 |
| `max_probability` | DECIMAL(5,4) | 해당 날짜의 최대 추론 확률 |
| `first_detected_at` | TIMESTAMP | 최초 감지 시각 |
| `last_detected_at` | TIMESTAMP | 마지막 감지 시각 |
| `model_artifact_id` | UUID | 판정에 사용한 모델, 모델 테이블 사용 시 참조 |
| `created_at` | TIMESTAMP | 생성 시각 |
| `updated_at` | TIMESTAMP | 수정 시각 |

### 수집 상태와 활동 결과를 분리한 이유

기존 한 테이블 구조에서는 한 가구의 `sample_count`, `coverage_ratio`, `observation_status`가
가전 6종 행마다 동일하게 반복된다.

```text
H001 / 9월 7일 / 전자레인지 / 수집률 95%
H001 / 9월 7일 / 전기포트   / 수집률 95%
H001 / 9월 7일 / 인덕션     / 수집률 95%
...
```

수집률은 가전별 정보가 아니라 가구 전체 센서의 상태다. 따라서 한 번만 저장하고,
가전별 활동 결과가 `observation_daily_id`로 그 행을 참조하도록 분리했다.

```text
household_observation_daily
H001 / 9월 7일 / 수집률 95% / VALID
    ├─ 전자레인지 / 사용
    ├─ 전기포트   / 사용
    ├─ 인덕션     / 미사용
    ├─ 전기다리미 / 미사용
    ├─ 헤어드라이기 / 사용
    └─ 진공청소기 / 미사용
```

`detected = false`와 센서 데이터 부족은 반드시 구분한다.

```text
activity_detected = false
→ 데이터는 정상적으로 들어왔지만 가전 사용이 감지되지 않음

observation_status = SENSOR_GAP
→ 데이터 자체가 부족해 가전 사용 여부를 판단할 수 없음
```

## ERD 관계 요약

```text
model_artifact
    1 ── N household_activity_daily

household_observation_daily
    1 ── N household_activity_daily

routine_baseline
    household_id + appliance_type 기준으로 활동 결과와 비교

analysis_policy
    일 단위 활동 결과에 이상 판단 규칙 적용
```

- `household_observation_daily`: `UNIQUE(household_id, observation_date)`
- `household_activity_daily`: `UNIQUE(observation_daily_id, appliance_type)`
- `routine_baseline`: `UNIQUE(household_id, appliance_type, baseline_type)`
- 가구 정보가 다른 DB에 있다면 `household_id`는 물리 FK 없이 논리 식별자로 사용한다.

## 남은 결정 사항

1. 실제 센서와 Kafka 메시지가 AI 입력 4종을 제공할 수 있는지 확인
2. 299초 입력이 과거 299초인지, 후보 시점 전후를 포함하는 중심 윈도우인지 AI 파트와 확정
3. 체크포인트에 6종 출력 순서와 threshold가 포함됐는지 확인
4. 모델 파일과 `manifest.json`의 배포·로딩 방식 확정
5. 새 가구의 최초 기준선 생성에 필요한 최소 유효 관측일 확정
6. `reliability_weight` 계산식 확정
7. 연속 활동 미감지 기준 D=1/2/3 및 쿨다운 확정
8. `model_artifact`를 MVP DB에 둘지, 모델을 서비스에 고정 배포할지 결정

## 오늘의 결론

- 초기 구현은 Flink 없이 Python Kafka Consumer로 시작한다.
- AI는 6종 가전을 동시에 출력하는 멀티라벨 모델로 취급한다.
- `analysis_db`는 원본 전력 저장소가 아니라 분석 메타데이터와 일 단위 활동 집계 저장소다.
- MVP ERD는 모델 정보, 기준선, 분석 정책, 가구별 관측 상태, 가전별 활동 결과를 중심으로 구성한다.
- 알고리즘별 가변 설정은 JSONB에 두되, 의미가 명확하고 자주 조회하는 값은 일반 컬럼으로 유지한다.
