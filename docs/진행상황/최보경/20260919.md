# 2026-09-19 진행상황

작성자: 최보경

## 오늘 작업 요약

모니터링 서비스의 외출 시작·종료 이벤트를 AI 분석 서비스가 수신하여 다음 두 패턴에 반영하도록 구현했다.

- `PROLONGED_INACTIVITY`: 외출 중 감지를 보류하고, 귀가 이후부터 수면시간을 제외한 미활동 시간을 다시 계산한다.
- `ROUTINE_MISSED`: 해당 가전의 예상 첫 사용 시간대와 외출 구간이 겹친 날은 그 가전의 누락 판단을 제외한다.

전체 흐름은 다음과 같다.

```text
모니터링 서비스 외출 상태 변경
  -> monitoring.household-presence.v1
  -> AI OutingEventConsumer
  -> household_outing_state
  -> ROUTINE_MISSED / PROLONGED_INACTIVITY 판단
  -> analysis.event.v1
```

---

## 1. 외출 이벤트 계약 및 Consumer 설정

수신 토픽과 메시지 계약을 정의했다.

| 항목 | 값 |
| --- | --- |
| 입력 토픽 | `monitoring.household-presence.v1` |
| Kafka Key | `household_id` |
| Consumer Group | `realtime-analysis-service-outing-v1` |
| 지원 이벤트 | `OUTING_STARTED`, `OUTING_ENDED` |
| Offset 처리 | 정상 저장 후 수동 커밋 |
| 잘못된 메시지 | `dlq.analysis` 전송 후 커밋 |

```json
{
  "event_id": "5fd787c0-f20f-42b9-a404-7baf53af990a",
  "household_id": "H001",
  "event_type": "OUTING_STARTED",
  "occurred_at": "2026-09-19T07:30:00+09:00"
}
```

동일한 `event_id`가 재수신되거나 이미 처리한 시각보다 오래된 이벤트가 도착하면 상태를 되돌리지 않고 무시한다. 정상적으로 무시한 메시지는 재처리가 필요하지 않으므로 offset을 커밋한다.

## 2. 외출 상태 저장

### `household_outing_state`

가구별 현재 외출 여부와 가장 최근 외출 구간을 한 행에 저장하는 유일한 외출 테이블이다.

| 주요 컬럼 | 용도 |
| --- | --- |
| `household_id` | 가구 식별자 |
| `is_outing` | 현재 외출 여부 |
| `outing_started_at` | 가장 최근 외출 시작 시각. 귀가 후에도 유지 |
| `last_returned_at` | 가장 최근 귀가 시각 |
| `last_event_id` | 마지막으로 반영한 이벤트 ID |
| `last_event_at` | 마지막으로 반영한 이벤트 발생 시각 |

별도 외출 이력 테이블은 만들지 않는다. `ROUTINE_MISSED`는 상태 행에 남은 가장 최근
외출 시작·종료 시각과 판단 구간의 겹침만 확인한다. 여러 과거 외출 구간을 장기 조회하는
기능은 MVP 범위에 포함하지 않는다.

현재 Alembic 최신 revision은 `20260919_09`이다.

`20260919_08`이 이미 적용된 로컬 DB도 안전하게 정리해야 하므로 해당 migration 파일을
삭제하거나 수정하지 않았다. 대신 `20260919_09`가 최근 외출 시각을 상태 행으로 옮긴 뒤
`household_outing_period`를 삭제한다. 최종 스키마에는 외출 테이블이 하나만 남는다.

## 3. 전용 Kafka Consumer 구현

원천 전력 데이터 Consumer와 별도로 외출 이벤트 전용 Consumer를 실행하도록 서비스 생명주기에 연결했다.

- 서비스 시작 시 두 Consumer가 각각 독립된 스레드에서 실행된다.
- 서비스 종료 시 두 Consumer를 모두 안전하게 중지한다.
- 외출 토픽이 없으면 readiness 검사가 실패하도록 구성했다.
- DB 저장 실패 시 offset을 커밋하지 않고 서비스 오류로 처리하여 메시지가 유실되지 않게 했다.
- JSON 파싱 또는 계약 검증 실패 메시지는 `dlq.analysis`로 전달한다.

## 4. 외출을 반영한 패턴 감지

### `PROLONGED_INACTIVITY`

현재 규칙은 다음과 같다.

1. 현재 외출 중이면 감지를 보류한다.
2. 귀가한 경우 미활동 시작 시각을 `max(마지막 가전 활동 시각, 최근 귀가 시각)`으로 정한다.
3. `23:00~07:00` 수면 구간은 미활동 시간에서 제외한다.
4. 깨어 있을 것으로 예상되는 시간의 미활동이 6시간에 도달하면 이벤트를 발행한다.
5. 열려 있는 가전 사용 세션이 있으면 미활동으로 판단하지 않는다.

예를 들어 마지막 활동이 10:00이고 17:00에 외출하여 22:00에 귀가했다면 계산 시작점은 22:00이다. 22:00~23:00의 1시간과 다음 날 07:00~12:00의 5시간을 합산하여 12:00에 6시간 조건을 만족한다.

### `ROUTINE_MISSED`

가전별 `routine_baseline.expected_until`까지 평소 사용하던 가전이 사용되지 않았는지 판단한다. 해당 가전의 판단 구간과 외출 구간이 겹치면 그 날짜·가전 조합만 누락 판단에서 제외한다.

현재 기준선에는 예상 시작 시각이 없으므로 판단 구간은 가구 로컬 날짜의 `00:00~expected_until`이다. 향후 더 좁은 예상 사용 구간이 필요하면 기준선에 `expected_from`을 추가할 수 있다.

### 변경하지 않은 패턴

- `PROLONGED_APPLIANCE_USE`: 외출 중에도 위험 가전의 장시간 사용은 위험하므로 그대로 감지한다.
- `ROUTINE_CHANGED`: 여러 유효 날짜의 사용 패턴 변화로 판단하므로 이번 외출 상태 연동 대상에서 제외했다.

## 5. 테스트 결과

실제 Repository와 패턴 감지기를 연결하고 Kafka 입력 경계만 테스트 대역으로 둔 통합 테스트를 추가했다.

검증한 항목은 다음과 같다.

- `OUTING_STARTED`와 `OUTING_ENDED` 수신 및 단일 상태 행 갱신
- 외출 구간과 겹치는 가전만 `ROUTINE_MISSED` 판단 제외
- 외출 중 `PROLONGED_INACTIVITY` 미발행
- 귀가 시각부터 미활동 계산 재시작
- `23:00~07:00` 수면 구간 제외
- 깨어 있는 시간 6시간 충족 시 이벤트 1회 발행

전체 테스트 결과:

```text
104 passed
```
