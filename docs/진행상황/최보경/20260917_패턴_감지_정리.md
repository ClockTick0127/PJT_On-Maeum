작성자: 최보경

> **2026-09-19 변경사항:** `PROLONGED_INACTIVITY`는 외출 중 보류하고 귀가 후부터 수면시간을 제외한 6시간을 계산한다. `ROUTINE_MISSED`는 예상 첫 사용 판단 구간과 외출 구간이 겹치면 해당 날짜·가전을 제외한다. 최신 내용은 `20260919_외출_이벤트_모니터링_전달_운영_테스트.md`를 참고한다.

## 1. 전체 구조

실시간 분석 서비스가 만드는 결과는 위험 이벤트, 정보성 이벤트, 일일 활동 지수,
데이터 품질 이벤트로 구분한다. 분석 서비스는 감지 근거만 발행하며 최종 위험 점수와
Incident, 사용자 알림은 Monitoring 서비스에서 계산하고 생성한다.

| 분류 | 유형 | 전달 토픽 | 위험 점수 반영 | 처리 목적 |
| --- | --- | --- | --- | --- |
| 위험 이벤트 | `ROUTINE_MISSED` | `analysis.event.v1` | 반영 | 평소 사용하던 가전의 사용 누락 감지 |
| 위험 이벤트 | `PROLONGED_INACTIVITY` | `analysis.event.v1` | 반영 | 가구 전체 활동의 장시간 부재 감지 |
| 위험 이벤트 | `PROLONGED_APPLIANCE_USE` | `analysis.event.v1` | 반영 | 위험 가전의 장시간 연속 사용 감지 |
| 정보성 이벤트 | `ROUTINE_CHANGED` | `analysis.event.v1` | 미반영 | 생활 시간대 변화 이력 표시 및 재기준화 판단 보조 |
| 일일 지표 | `activity_index` | `analysis.activity.v1` | Monitoring에서 반영 | 하루 절대 활동량 전달 |
| 데이터 품질 | `DATA_GAP` | `analysis.data-quality.v1` | 미반영 | 실시간 입력 공백 상태 알림 |
| 데이터 품질 | `DATA_RECOVERED` | `analysis.data-quality.v1` | 미반영 | 입력 수집 복구 알림 |

```text
power.raw.v1
  ├─ 실시간 모델 추론 및 ON/OFF 히스테리시스
  │    ├─ 가전 사용 세션 저장
  │    ├─ 위험 이벤트 감지
  │    └─ analysis.snapshot.v1 발행
  │
  ├─ 가구별 실제 입력 수신 시각 추적
  │    └─ analysis.data-quality.v1 발행
  │
  └─ 매일 00:10 전날 데이터 마감
       ├─ analysis.activity.v1 발행
       ├─ ROUTINE_CHANGED 판단
       └─ routine_baseline 갱신
```

## 2. 공통 Event 계약

위험 이벤트와 정보성 이벤트는 `analysis.event.v1`으로 발행한다. Kafka Record Key는
`household_id`이고 Value는 UTF-8 JSON Object다.

```json
{
  "event_id": "1bb4edcf-77ae-44d6-ad7c-b87a6e071f5a",
  "household_id": "H001",
  "event_type": "ROUTINE_MISSED",
  "occurred_at": "2026-09-16T23:10:00Z",
  "reason": {}
}
```

| 필드 | 의미 |
| --- | --- |
| `event_id` | 논리 이벤트 정보를 이용해 결정적으로 생성한 UUID |
| `household_id` | 이벤트가 발생한 가구 ID |
| `event_type` | 감지한 패턴 유형 |
| `occurred_at` | 해당 조건이 성립한 시각 |
| `reason` | 이벤트별 판정 근거 JSON Object |

분석 서비스는 `score`와 `severity`를 발행하지 않는다. 동일한 논리 이벤트는 재시작이나
재처리 후에도 같은 `event_id`를 사용하므로 Monitoring 서비스는 `event_id`를 기준으로
멱등 처리한다.

## 3. `ROUTINE_MISSED`

### 목적

가구가 평소 자주 사용하던 특정 가전을 기준 시각까지 사용하지 않은 경우를 감지한다.

### 판단 순서

1. `routine_baseline`에서 현재 가구와 요일에 적용할 활성 기준선을 조회한다.
2. 다음 식으로 기준선 강도를 계산한다.

```text
baseline_strength
  = normal_days / window_days × 100 × reliability_weight
```

3. 기본 최소 강도인 80 이상인 기준선만 사용한다.
4. 현재 시각이 기준선의 `expected_until`을 지났는지 확인한다.
5. 당일 자정부터 `expected_until`까지 해당 가전의 유효 사용 세션이 있는지 확인한다.
6. 같은 구간과 겹치는 외출 구간이 있으면 해당 날짜·가전의 판단을 제외한다.
7. 사용 세션과 외출 구간이 모두 없으면 이벤트를 발행한다.

예를 들어 최근 14일 중 12일 동안 전자레인지를 08:10 이전에 사용했는데 오늘은 해당
시각까지 사용하지 않았다면 이벤트가 발생한다.

### `reason`

```json
{
  "appliance_type": "MICROWAVE",
  "expected_until": "08:10",
  "normal_days": 12,
  "window_days": 14
}
```

| 필드 | 의미 |
| --- | --- |
| `appliance_type` | 예정 시각까지 사용되지 않은 가전 |
| `expected_until` | 평소 사용이 기대되는 마감 시각 |
| `normal_days` | 기준 기간 중 해당 가전을 사용한 일수 |
| `window_days` | 기준선 표본 기간의 유효 관측일 수 |

`occurred_at`은 실제 검사 시각이 아니라 루틴 사용 마감 시각이다. 기본 cooldown은
24시간이며 같은 가전과 날짜의 이벤트 ID는 동일하다.

## 4. `PROLONGED_INACTIVITY`

### 목적

특정 가전 하나가 아니라 가구 전체에서 장시간 아무 가전 활동도 확인되지 않는 상태를
감지한다.

### 판단 순서

1. 현재 열린 가전 세션이 하나라도 있으면 판단하지 않는다.
2. 현재 외출 중이면 판단을 보류한다.
3. 전체 대상 가전 중 마지막으로 완료된 사용 세션의 종료 시각과 최근 귀가 시각을
   조회한다.
4. `max(마지막 활동 시각, 최근 귀가 시각)`을 미활동 계산 시작점으로 사용한다.
5. 매일 `23:00~07:00` 수면 구간은 미활동 누적시간에서 제외한다.
6. 깨어 있을 것으로 예상되는 시간의 미활동이 6시간에 도달하면 이벤트를 발행한다.

`ROUTINE_MISSED` 여러 건과 의미가 유사해 보일 수 있지만 판단 대상이 다르다.

| 비교 | `ROUTINE_MISSED` | `PROLONGED_INACTIVITY` |
| --- | --- | --- |
| 판단 단위 | 특정 가전의 평소 루틴 | 가구 전체 가전 활동 |
| 기준 | 기준선의 예상 사용 시각 | 마지막 전체 활동 이후 경과시간 |
| 발생 예 | 아침 전자레인지 루틴 누락 | 외출·수면을 제외하고 모든 대상 가전을 6시간 동안 사용하지 않음 |

### `reason`

```json
{
  "last_activity_at": "2026-09-19T01:00:00Z",
  "last_returned_at": "2026-09-19T13:00:00Z",
  "inactivity_started_at": "2026-09-19T13:00:00Z",
  "threshold_hours": 6.0,
  "sleep_window": {
    "start": "23:00",
    "end": "07:00"
  }
}
```

| 필드 | 의미 |
| --- | --- |
| `last_activity_at` | 가장 최근에 완료된 가전 활동 시각 |
| `last_returned_at` | 가장 최근 귀가 시각. 없으면 `null` |
| `inactivity_started_at` | 마지막 활동과 귀가 시각 중 더 늦은 실제 계산 시작점 |
| `threshold_hours` | 수면을 제외한 장시간 미활동 판정 기준 시간 |
| `sleep_window` | 미활동 누적에서 제외한 가구 로컬 수면시간 |

`occurred_at`은 `inactivity_started_at`부터 수면 구간을 제외하여 6시간을 모두 누적한
시각이다. 기본 cooldown은 12시간이다.

## 5. `PROLONGED_APPLIANCE_USE`

### 목적

장시간 켜져 있을 때 실제 위험 가능성이 있는 가전만 대상으로 허용 시간을 초과한 연속
사용을 감지한다.

### 현재 대상과 기준

| 가전 | 기본 허용시간 |
| --- | ---: |
| 인덕션 `INDUCTION` | 120분 |
| 다리미 `IRON` | 60분 |

열린 `appliance_usage_session`의 `started_at`에 가전별 허용 시간을 더한 시각이 현재
시각보다 이전이면 이벤트를 발행한다. 전기포트, 전자레인지, 헤어드라이기, 진공청소기는
현재 위험 이벤트 대상에 포함하지 않는다.

### `reason`

```json
{
  "appliance_type": "INDUCTION",
  "started_at": "2026-09-17T05:00:00Z",
  "allowed_duration_minutes": 120.0
}
```

| 필드 | 의미 |
| --- | --- |
| `appliance_type` | 허용 시간을 초과한 가전 |
| `started_at` | 현재 열린 사용 세션의 시작 시각 |
| `allowed_duration_minutes` | 해당 가전에 설정된 허용 사용시간 |

`occurred_at`은 `started_at + allowed_duration_minutes`이고 같은 사용 세션에는 결정적인
이벤트 ID가 부여된다. 기본 cooldown은 24시간이다.

## 6. `ROUTINE_CHANGED`

### 목적과 분류

최근 생활 시간대가 이전 패턴보다 지속적으로 이동했는지 확인하는 정보성 이벤트다.
사용자가 위험하다는 의미가 아니므로 위험 점수에는 반영하지 않는다.

### 현재 구현 방식

매일 전날 데이터가 마감된 후 가전별 일일 첫 사용 시각을 비교한다.

1. `VALID` 상태인 관측일만 사용한다.
2. 최근 7일과 그 이전 21일을 비교한다.
3. 최근 구간은 최소 5일, 이전 구간은 최소 14일의 유효 관측이 있어야 한다.
4. 양쪽 기간 모두 해당 가전의 사용확률이 70% 이상이어야 한다.
5. 각 기간의 일별 첫 사용 시각 중앙값을 계산한다.
6. 두 중앙값이 120분 이상 이동하면 이벤트를 발행한다.

10초 미만 사용은 첫 사용으로 인정하지 않는다. 히스테리시스로 생성된 인접 세션은
가전별 병합 간격을 적용해 하나의 논리적 사용으로 합친다. 자정 부근의 변화는 원형 시간
차이를 사용하여 `23:30 → 00:30`을 23시간이 아니라 1시간 이동으로 계산한다.

### `reason`

```json
{
  "appliance_type": "MICROWAVE",
  "change_type": "FIRST_USE_TIME_SHIFT",
  "direction": "LATER",
  "previous_time": "08:00",
  "recent_time": "10:30",
  "shift_minutes": 150,
  "recent_valid_days": 7,
  "reference_valid_days": 20
}
```

| 필드 | 의미 |
| --- | --- |
| `appliance_type` | 시간대 변화가 감지된 가전 |
| `change_type` | 현재는 첫 사용 시각 이동인 `FIRST_USE_TIME_SHIFT` |
| `direction` | 늦어지면 `LATER`, 빨라지면 `EARLIER` |
| `previous_time` | 이전 21일의 첫 사용 시각 중앙값 |
| `recent_time` | 최근 7일의 첫 사용 시각 중앙값 |
| `shift_minutes` | 시각 변화량. 늦어지면 양수, 빨라지면 음수 |
| `recent_valid_days` | 최근 구간의 가구 유효 관측일 수 |
| `reference_valid_days` | 이전 구간의 가구 유효 관측일 수 |

`routine_baseline`은 이벤트와 무관하게 하루 한 번 자동 갱신된다. 따라서 현재
`ROUTINE_CHANGED`는 기준선 재계산 트리거가 아니라 생활 패턴 변경 이력과 알고리즘 설명을
위한 이벤트다. Monitoring이나 화면에서 이 이력을 사용하지 않는다면 MVP 발행 대상에서
제외하는 것도 가능하다.

현재 중복 억제 상태는 프로세스 메모리에 있고, 같은 방향과 30분 단위 최근 시각 구간이
유지되면 다시 발행하지 않는다. 정책에는 `cooldown_hours=168`이 있으나 현재 일일 감지
코드에서는 이 값을 직접 적용하지 않는다.

## 7. 일일 `activity_index`

### 목적

위험 점수가 아니라 하루 동안 실제로 얼마나 활동했는지를 나타내는 0~100 절대 지수다.
한국 시간 기준 매일 00:10에 전날 지수를 한 번 계산하여 `analysis.activity.v1`으로
발행한다.

### 계산식

```text
usage_count_score
  = min(점수 반영 사용 횟수 / 6, 1) × 100

appliance_diversity_score
  = min(사용한 가전 종류 수 / 3, 1) × 100

usage_duration_score
  = min(점수 반영 사용시간 / 3,600초, 1) × 100

activity_index
  = 0.50 × usage_count_score
  + 0.30 × appliance_diversity_score
  + 0.20 × usage_duration_score
```

같은 가전의 사용 횟수는 점수에 하루 최대 3회까지만 반영한다. 실제 원본 사용 횟수는
`components.usage_count`에 유지한다.

사용시간도 장시간 사용 하나가 활동 지수를 계속 올리지 않도록 점수 계산에만 가전별
상한을 적용한다.

| 가전 | 점수 반영 일일 상한 |
| --- | ---: |
| 전기포트 | 10분 |
| 전자레인지 | 30분 |
| 헤어드라이기 | 30분 |
| 다리미 | 60분 |
| 진공청소기 | 90분 |
| 인덕션 | 180분 |

### 계약

```json
{
  "message_id": "8f3b2a19-4d6e-4c72-9b12-a1b2c3d4e5f6",
  "household_id": "H001",
  "activity_date": "2026-09-16",
  "activity_index": 85,
  "data_status": "VALID",
  "components": {
    "usage_count": 5,
    "appliance_type_count": 3,
    "usage_duration_seconds": 2400,
    "usage_count_score": 83,
    "appliance_diversity_score": 100,
    "usage_duration_score": 67
  }
}
```

관측이 부족한 날은 활동이 0인 날이 아니므로 0점으로 변환하지 않는다.

```json
{
  "message_id": "8f3b2a19-4d6e-4c72-9b12-a1b2c3d4e5f6",
  "household_id": "H001",
  "activity_date": "2026-09-16",
  "activity_index": null,
  "data_status": "INSUFFICIENT_DATA"
}
```

Monitoring 서비스는 `VALID` 지수만 저장·집계하며 `activity_index`와 component 점수를
동시에 위험 점수에 합산하면 안 된다. Component 점수는 최종 지수의 계산 근거이므로 둘을
함께 더하면 같은 활동이 중복 반영된다. 위험 계산에는 최종 지수만 사용하고 components는
화면 설명과 디버깅에 사용한다.

## 8. `routine_baseline` 생성 및 갱신

기준선은 샘플마다 갱신하지 않고 하루 한 번 갱신한다. 전날 활동 지수와 정보성 이벤트를
처리한 뒤 최근 데이터를 이용해 같은 행을 UPSERT한다.

```text
최근 28일 조회
  → VALID 날짜만 선택
  → 최소 14일 이상인지 확인
  → 가구·가전별 사용일과 첫 사용 시각 계산
  → routine_baseline UPSERT
```

```text
sample_days = 최근 계산 구간의 VALID 날짜 수
active_days = 해당 가전을 10초 이상 사용한 VALID 날짜 수
daily_use_probability = active_days / sample_days
reliability_weight = min(sample_days / 최소 표본일, 1)
```

전체 첫 사용 시각의 P90을 `expected_until`로 사용한다. 해당 요일의 유효 표본이 기본
4일 이상이면 요일별 P90을 우선 사용하고 부족하면 전체 요일 기준으로 대체한다. 일
사용확률이 기본 0.70 이상이고 첫 사용 시각이 존재하는 행만 활성화한다.

`INSUFFICIENT_DATA`, `SENSOR_GAP`, 처리 실패일은 기준선 표본에서 제외한다. 초기
`config/baselines.json` 값은 DB에 해당 키가 없을 때만 부트스트랩하며, 충분한 실제
`VALID` 데이터가 쌓이면 계산 결과로 교체한다.

## 9. `DATA_GAP`과 `DATA_RECOVERED`

### 감지 기준

현재 데이터 공백은 센서 메시지의 `measured_at` 차이가 아니라 분석 서비스가 유효한
Kafka 입력을 실제로 받은 시각을 기준으로 감지한다.

```text
마지막 정상 입력 수신
  → 실제 수신 공백이 기준시간 이상 지속
  → DATA_GAP 1회 발행
  → 최신 측정값 3개 수신
  → DATA_RECOVERED 1회 발행
```

운영 기본값은 공백 120초, watchdog 검사 주기 5초, 복구 확인 샘플 3개다. 로컬 테스트는
공백 10초와 검사 주기 1초로 변경할 수 있다.

### `DATA_GAP` 계약

```json
{
  "event_id": "uuid",
  "household_id": "H001",
  "event_type": "DATA_GAP",
  "occurred_at": "2026-09-17T10:02:00+09:00",
  "reason": {
    "last_valid_received_at": "2026-09-17T10:00:00+09:00",
    "gap_seconds": 120
  }
}
```

| 필드 | 의미 |
| --- | --- |
| `last_valid_received_at` | 마지막 정상 Kafka 입력 수신 시각 |
| `gap_seconds` | 감지 시점까지 실제 입력이 없었던 시간 |

### `DATA_RECOVERED` 계약

```json
{
  "event_id": "uuid",
  "household_id": "H001",
  "event_type": "DATA_RECOVERED",
  "occurred_at": "2026-09-17T10:05:05+09:00",
  "reason": {
    "last_valid_received_at": "2026-09-17T10:00:00+09:00",
    "gap_detected_at": "2026-09-17T10:02:00+09:00",
    "gap_seconds": 305
  }
}
```

| 필드 | 의미 |
| --- | --- |
| `last_valid_received_at` | 공백이 시작되기 전 마지막 정상 수신 시각 |
| `gap_detected_at` | 공백 기준을 초과하여 `DATA_GAP`을 발행한 시각 |
| `gap_seconds` | 마지막 정상 수신부터 복구까지의 전체 공백 시간 |

공백 상태와 복구 확인 중에는 위험 이벤트 판단을 중단한다. 공백 전에 열린 가전 세션은
마지막 유효 측정 시각에서 종료하며, 복구 첫 입력에서 모델 버퍼와 히스테리시스 상태를
초기화한다. `DATA_RECOVERED`는 3개 입력 후 발행되지만 모델 추론은 299개 입력 버퍼가
다시 채워진 뒤 재개된다.

시뮬레이터의 일시정지로 MQTT와 Kafka 입력이 실제로 멈춘다면 시뮬레이션 시각이
정지하더라도 현재 방식의 `DATA_GAP`을 테스트할 수 있다. 반대로 `measured_at` 자체가
중간 시간을 건너뛰는 센서 타임스탬프 공백 감지는 현재 별도로 구현하지 않았다.

### DLQ와의 차이

| 구분 | 의미 | 전달 경로 |
| --- | --- | --- |
| `DATA_GAP` | 메시지 자체가 일정 시간 도착하지 않음 | `analysis.data-quality.v1` |
| DLQ | 도착한 메시지가 잘못됐거나 처리에 실패함 | `dlq.analysis` |

메시지가 존재하지 않는 상황은 실패한 원본 메시지가 없으므로 DLQ로 보낼 수 없다.

## 10. Monitoring 서비스 책임

Monitoring 서비스는 분석 서비스의 결과를 다음 방식으로 사용한다.

1. `analysis.event.v1`의 세 위험 이벤트를 위험 점수에 반영한다.
2. `ROUTINE_CHANGED`는 위험 점수에서 제외하고 필요하면 이력과 그래프에 표시한다.
3. `analysis.activity.v1`의 `VALID` 지수만 활동 감소 위험 계산에 사용한다.
4. `INSUFFICIENT_DATA`를 0점으로 변환하지 않는다.
5. `DATA_GAP` 동안 활동 없음이나 낮은 활동 지수를 사용자 위험으로 해석하지 않는다.
6. `event_id`와 `message_id`를 기준으로 중복 이벤트와 지표를 멱등 처리한다.
7. 최종 위험 점수, Incident, 사용자 알림과 알림 cooldown을 담당한다.

활동 감소를 계산할 때는 직전 하루 값 하나보다 `VALID` 활동 지수의 EWMA와 현재 값을
비교하는 방식을 권장한다. 초기 EWMA `alpha`는 0.3을 사용할 수 있다. 일일 지수이므로
기존의 `15분 × 4회` 규칙은 사용할 수 없고, 낮은 활동 상태가 연속 며칠 유지되는지로
다시 정의해야 한다.

## 11. 현재 구현상 주의사항

- 데이터 품질 상태는 현재 분석 서비스 프로세스 메모리에 유지된다.
- 서비스가 시작된 후 정상 입력을 한 번 이상 받은 가구부터 실시간 공백 감시가 시작된다.
- 분석 서비스가 재시작되면 진행 중이던 데이터 공백 상태도 초기화된다.
- 데이터 품질 이벤트와 분석 이벤트는 At-least-once 전달을 전제로 수신 측에서 멱등
  처리해야 한다.
- `ROUTINE_CHANGED`는 기준선 갱신을 직접 제어하지 않으며 정보성 이력으로만 발행된다.
- 운영 임계값은 초기 MVP 값이므로 실제 가구 데이터를 수집한 뒤 분포를 기준으로 조정해야
  한다.
