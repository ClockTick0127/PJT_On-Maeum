## 3. 계획 전제

### 3.1 AI 모델 수령 지연

실제 체크포인트 전달이 늦어질 가능성이 높다. 따라서 모델 의존 작업을 크리티컬 패스에서
제외하고, 모델 무관 작업을 앞쪽에 배치한다.

모델 없이도 진행 가능한 근거는 다음과 같다.

- 정규화 `mean`, `std`와 가전별 `threshold`를 코드가 아닌 `config/model_manifest.json`에서만
  읽도록 구현돼 있어, 가중치 수령 후 변경할 코드가 거의 없다.
- TorchPredictor 구현에 필요한 것은 가중치가 아니라 모델 클래스 정의와 입력 shape이다.
  무작위 초기화된 더미 체크포인트만 있으면 로딩, 추론, shape 검증, 레이턴시 측정이 가능하다.
- 레이턴시 계측과 병목 분석은 Predictor 구현체와 무관하다.

### 3.2 AI 파트 요청 순서

전체를 한 번에 요청하지 않고 아래 순서로 분할 요청한다. 1번과 2번만 수령하면 일정이 밀리지 않는다.

| 순위 | 요청 내용 | 필요 시점 |
| ---: | --- | --- |
| 1 | 모델 클래스 정의 코드, 입력 shape이 `(N, 4, 299)`인지 `(N, 299, 4)`인지 확인 | 9/14 |
| 2 | 무작위 초기화 더미 체크포인트 `.pt` | 9/14 ~ 9/15 |
| 3 | Feature별 학습 데이터 `mean`, `std` | 수령 시점 무관 |
| 4 | 가전별 Validation `threshold` | 수령 시점 무관 |

### 3.3 모델 미수령 시 대응

`FakePredictor`는 설정한 가전에 `1.0`을 반환하므로 시연이 불가능하다.
유효전력 크기와 변화폭으로 6종을 판정하는 규칙 기반 Predictor를 구현해 시연 경로를 확보한다.

이는 임시방편이 아니라 AI 파트가 공식 비교 대상으로 사용한 총량 기준선과 같은 접근이다.
AI 파트 3주차 보고 기준 `NILM 0.858 vs 총량 규칙 0.785 (Balanced accuracy)`.

- 모델 미도착 시 E2E 시연이 가능하다.
- 모델 도착 시 동일 파이프라인에서 두 Predictor를 교체 비교한 실측값을 얻는다.
- Predictor 인터페이스가 실제로 교체 가능함을 증명한다.

발표 및 문서에서는 반드시 기준선(baseline)으로 명시하고 AI 모델로 표기하지 않는다.

### 5.1 S15P21D201-248 · 분산 처리 및 서비스 로직 고도화 (29 SP)

#### [BE] 단계별 구간 타이머 & 구조화 로그 기록 — 5

파이프라인 각 단계의 소요 시간을 개별 측정해 병목 구간을 특정한다.

측정 대상 단계는 다음과 같다.

```text
t0  measured_at            센서 및 시뮬레이터 측정 시각
t1  MQTT 수신              mqtt-kafka-bridge
t2  Kafka produce ack      power.raw.v1
t3  consumer poll 반환     consumer.py
t4  역직렬화 및 검증 완료   PowerMeasurement.model_validate
t5  버퍼 append 완료        buffer.append
t6  전처리 완료             preprocessing
t7  모델 추론 완료          predictor.predict
t8  판정 및 전이 감지 완료  state_decider, state_transition
t9  DB 트랜잭션 완료        activity_repository.record
t10 snapshot produce ack   snapshot_publisher
t11 monitoring 수신 및 SSE  monitoring-service
```

이 중 `t3` ~ `t10` 8단계가 본 서비스 담당 범위다.

작업 내용

- `time.perf_counter_ns()` 기반 구간 측정 컨텍스트 매니저를 추가한다.
  `with stage("inference"):` 형태로 `handler.py`가 지저분해지지 않게 한다.
- 메시지 1건 처리가 끝나면 전 구간 소요 시간을 JSON 한 줄로 기록한다.
- E2E 지연은 기존 Snapshot의 `published_at - observed_at`을 그대로 사용한다.

완료 조건

- 담당 8단계가 나노초 단위로 기록된다.
- 메시지당 구조화 로그 1줄이 출력되고 파싱 가능하다.

#### [BE] DB 쓰기 배치화 & 스냅샷 발행 최적화 — 5

현재 `handler.py`는 메시지 1건마다 다음을 수행한다.

1. `record_observation()` DB 쓰기
2. `record()` DB 트랜잭션 (`SELECT FOR UPDATE` 포함)
3. `snapshot_publisher.publish()` 동기 발행 및 결과 확인

110 msg/s 기준 초당 110회 이상의 DB 트랜잭션이 발생한다.
AI 파트가 보고한 TCN 단건 추론이 CPU 1.5ms인 점을 고려하면, 전체 지연의 대부분이
추론이 아닌 DB 구간에서 발생할 가능성이 높다.

작업 내용

- 일일 관측 카운트를 인메모리로 누적하고 주기적으로 flush한다.
- 상태 변화가 없는 구간의 불필요한 DB 접근을 제거한다.
- 스냅샷 발행 방식을 검토해 처리 경로에서 분리 가능한지 판단한다.
- 개선 전후를 동일 조건에서 재측정한다.

완료 조건

- 개선 전후 단계별 p95 비교표를 작성한다.
- 멱등성과 중복 방지 동작이 유지됨을 테스트로 확인한다.

### 5.4 S15P21D201-114 · 가구 전력 데이터 처리 & 패턴 분석 MVP 구현 (5 SP)

#### [BE] 일일 마감 배치 구현 & 관측 상태 확정 — 5

현재 `household_observation_daily`는 최초 생성 시 임시값으로 고정돼 있다.

```text
observation_status = COLLECTING
sample_count = 0
expected_sample_count = 86400
coverage_ratio = 0
```

작업 내용

- `sample_count`를 실시간 누적한다.
- `coverage_ratio = sample_count / expected_sample_count`를 계산한다.
- 관측 상태를 `VALID`, `INSUFFICIENT_DATA` 등으로 확정한다.
- 사용이 감지되지 않은 가전도 `event_count = 0` 행을 생성한다.
- 날짜 기준은 `Asia/Seoul`을 사용한다.

완료 조건

- FR-022 ~ FR-032를 충족한다.
- `COLLECTING` 고정 상태가 해소된다.
