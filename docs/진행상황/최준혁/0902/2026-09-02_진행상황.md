## 2. 상세 진행 내용

### (1) IoT 데이터 수집 파이프라인 구조 정립
* **ESP32 MCU의 한계 보완**: 가벼운 MQTT 프로토콜로 엣지 단말 부하를 최소화하고, 수집된 데이터를 Kafka로 버퍼링/분산 전달하는 표준 아키텍처 채택
* **데이터 흐름**:
  ```text
  [ 가구별 분전반 계측 (10가구) ]
                 │ (MQTT Publish: v1/power/sim/{house}/main)
                 ▼
     [ Mosquitto MQTT Broker ] (Port: 1883, 계정 인증)
                 │ (MQTT Subscribe)
                 ▼
       [ Kafka Connect ] (MQTT Source Connector)
                 │ (Produce: Key=house_id)
                 ▼
        [ Apache Kafka ] (Topic: raw-power-events)
                 │
                 ├──▶ NILM AI 모델 (가구별 전력 분해 추론)
                 ├──▶ Spring Boot 백엔드 (실시간 웹소켓 모니터링)
                 └──▶ PostgreSQL (시계열 데이터 통계 적재)
  ```

### (2) Mosquitto MQTT Broker 인프라 구축 (`mqtt_tools/`)
* **Docker 컨테이너화 (`compose.yaml`)**:
  - `eclipse-mosquitto:2` 이미지 기반 경량 브로커 컨테이너 구성
  - 프로젝트 공통 외부 네트워크인 `nilm-net`에 연동하여 백엔드/DB/Kafka와의 내부 컨테이너 통신 기반 마련
* **보안 및 자원 제어 정책 (`config/mosquitto.conf`)**:
  - 익명 접근 차단(`allow_anonymous false`) 및 암호화된 비밀번호 파일(`passwd`) 기반 인증 강제
  - `simulator_user`, `kafka_bridge_user` 역할별 전용 계정 발급
  - 브로커 단 디스크 영구 저장 비활성화(`persistence false`)로 메모리 최적화 및 I/O 병목 제거

### (3) 가구별 메인 분전반 전력 데이터 시뮬레이터 개발 (`simulator.py`)
* **NILM 특화 데이터 모델링**:
  - **대상**: 총 10개 가구 (`H001` ~ `H010`)
  - **가전 6종 모델링**: 냉장고(컴프레서 주기 동작), TV, 에어컨, 세탁기, 전자레인지, 조명
  - **상시 기저부하(Base Load)**: 대기전력(25~45W) 및 센서 노이즈 모델링
  - **집계(Aggregation)**: 가전별 ON/OFF 상태에 따른 소비 전력을 실시간 합산하여 **가구별 메인 분전반 총 소비 전력(`power_w`)** 산출
* **발행 토픽 및 메시지 규격**:
  - **Topic**: `v1/power/sim/{house}/main` (1초 주기 발행)
  - **JSON Payload**:
    ```json
    {
      "house": "H001",
      "device": "main",
      "ts": "2026-09-02T06:50:00.123Z",
      "power_w": 1245.35
    }
    ```

### (5) Kafka brdige 관련 조사
  **Kafka Connect**

  - **kafka 중심 분산 통합 아키텍처** :  수많은 소스/싱크와 Kafka를 연결하기 위해 Apache Kafka가 공식 제공하는 컴포넌트
  - **오프셋 및 상태 추적의 완벽성** : 수신한 위치 정보를 Kafka 내부 토픽에 지속적으 커밋한다. 시스템이 다운되었다가 재시작되어도 중복이나 유실 없이 정확히 멈춘 시점부터 다시 데이터를 이어받는다.
  - **스키마 변환 및 거버넌스** : Avro, Protobuf, JSON Schema 등과 결합할 때, 플러기인단에서 스키마 유효성을 검증하고 압축 바이너리로 변환해주는 기능이 프레임워크 레벨에서 완성되어 있다.

  단점 : 단일 도커 컨테이너를 올리더라도 JVM 힙 메모리를 기본으로 소모하며, 플러그인 설치 및 REST API 등록 등 초기 러닝 커브와 인프라 관리 비용이 크다

  **Telegraf**

  - **Go 기반의 초경량 법용 수집기** : 원래 시계열 데이터베이스 전송용으로 설계되었다.
  - **극도로 단순한 배포 및 운영** : 별도의 REST 통신이나 플러그인 빌드 없이 파일에 입력과 출력 블록만 적어두면 즉시 실행됨
  - **시스템 오버헤드 최소화** : 컨테이너 1개당 수십 MB 수준의 RAM만 사용하므로 로컬 개발머신이나 엣지 게이트웨이 기기에서도 리소스 부담 없이 구동이 가능하다.

  단점:  오프셋을 동기화하는 기능이 취약하다. 데이터의 구조를 기계적으로 검증하거나 Kafka의 고유 바이너리 직렬화 규격을 다루기 어렵다.

  | **구분**                       | **Kafka Connect**                                            | **Telegraf 에이전트**                                    |
  | ------------------------------ | ------------------------------------------------------------ | -------------------------------------------------------- |
  | **태생 및 목적**               | Apache Kafka 생태계 전용 대규모 데이터 파이프라인 프레임워크 | InfluxData에서 개발한 시계열 메트릭/데이터 수집 에이전트 |
  | **구현 방식**                  | Java 기반 분산 런타임 (Worker 프로세스)                      | Go 기반 단일 바이너리 경량 프로세스                      |
  | **인터페이스**                 | REST API를 통한 동적 커넥터 등록 및 제어                     | 단일 텍스트 설정 파일(`telegraf.conf`) 기반 정적 제어    |
  | **내결함성 (Fault Tolerance)** | 오프셋(Offset) 및 상태를 Kafka 토픽에 저장, 자동 복구 지원   | 프로세스 재시작 시 메모리 버퍼 데이터 유실 가능성 존재   |
  | **시스템 리소스 소모**         | JVM 구동으로 메모리 기본 점유율 높음 (약 1~2GB 권장)         | 메모리 점유율 수십 MB 수준으로 매우 가볍고 빠름          |

  ### Kafka Connect

  **Confluent MQTT Source Connector**

  - **Kafka 공식 지원 및 안정성** : 최신 Kafka 버전 및 생태계 기능과의 호환성이 가장 뛰어나다.
  - **Confluent 생태계와의 완벽한 통합** : MQTT로 들어온 데이터를 별도 변환 레이어 없이 Confluent Schema Registry와 연계하여 즉시 Kafka에 적재 가능하다.
  - **고급 데이터 변환 및 보완 기능 지원**

  단점 : 유료임 (로컬 평가판 30일 있긴함)

  **Lenses.io Stream Reactor MQTT Connector**

  - **KCQL 지원** : 자체 쿼리 문법인 KCQL을 제공한다. KCQL은 SQL과 유사한 문법으로 데이터 라우팅, 필드 매핑, 변환 등을 정의한다.
  - 오픈소스 진영에서 Confluent 대체재로 많이 사용됨
