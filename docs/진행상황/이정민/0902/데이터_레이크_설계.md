# NILM 데이터 레이크 설계

> 참고 글: [2일차_데이터레이크 아키텍처 설계 (람다 vs 카파 아키텍처)](https://velog.io/@mediaramy/lamdakappa1)
>
> 작성 기준일: 2026-09-02

## 1. 문서 목적

이 문서는 다가구 전력 센서 기반 NILM 서비스에서 다음 요구사항을 함께 만족하기 위한 데이터 레이크 구조를 정의한다.

- 가구별 전력 데이터를 실시간으로 수집하고 가전 상태와 생활 이상 징후를 빠르게 탐지한다.
- 원천 데이터를 장기간 보존해 장애 복구, 재처리, 모델 재학습에 사용한다.
- 실시간 결과와 과거 루틴 통계를 대시보드에서 함께 조회한다.
- 모델·전처리·데이터 버전을 추적해 특정 판단의 근거를 재현한다.
- 현재 EC2 자원에서는 가볍게 시작하되 가구 수 증가 시 관리형 서비스로 확장할 수 있게 한다.

## 2. 참고 블로그에서 가져갈 핵심

### 2.1 Lambda 아키텍처

Lambda 아키텍처는 데이터를 목적과 지연 시간에 따라 세 계층으로 구분한다.

| 계층 | 블로그의 설명 | NILM에서의 해석 |
|---|---|---|
| Batch Layer | 전처리·집계된 과거 데이터와 마스터 정보를 보관 | 원천 이력, 학습 데이터, 가구별 루틴 기준선 |
| Speed Layer | 배치에 아직 반영되지 않은 당일·실시간 데이터를 처리 | 현재 전력 Window, 가전 ON/OFF, 실시간 이상 이벤트 |
| Serving Layer | Batch와 Speed의 결과를 빠르게 조회하도록 제공 | Redis 최신 상태, PostgreSQL 이벤트 이력, 대시보드 API |

Lambda 아키텍처가 적합한 상황은 과거 기준선이나 마스터 정보와 실시간 데이터를 결합해야 할 때다. NILM에서는 “최근 14일간 아침 전기포트 사용 시각”과 “오늘 현재까지의 사용 여부”를 함께 판단하므로 이 개념이 유효하다.

단점은 배치 로직과 실시간 로직을 별도로 개발하면 같은 계산을 두 번 구현하게 되고, 결과가 서로 달라질 수 있다는 점이다.

### 2.2 Kappa 아키텍처

Kappa 아키텍처는 모든 이벤트를 메시지 로그에 넣고 하나의 스트림 처리 경로로 신규 데이터와 과거 재처리를 모두 수행한다.

NILM에 적용하면 다음 구조가 된다.

```text
신규 센서 데이터 → Kafka power.raw.v1 → Realtime Analysis
과거 S3 데이터   → Kafka power.replay.v1 → 동일 Realtime Analysis
```

이 방식은 신규 데이터와 재처리에 동일한 전처리·이벤트 탐지·모델 추론 코드를 사용할 수 있어 결과 불일치를 줄인다.

다만 모든 외부 데이터를 Kafka로만 수집할 필요는 없다. AI-Hub 학습 데이터, 모델 파일, 정기 마스터 데이터처럼 실시간성이 없는 대용량 파일은 배치 방식으로 S3에 직접 적재하는 편이 단순하다.

### 2.3 Kafka + Spark에서 확장할 수 있는 요소

블로그는 기본 실시간 흐름을 `Kafka → Spark Streaming`으로 설명하고, 확장 단계에서 다음 요소를 추가한다.

- Kafka Connect: 외부 시스템과 Kafka 사이의 표준 수집·배출 경로
- Debezium: 관계형 DB 변경을 CDC 이벤트로 변환
- Redis: 대시보드·알림을 위한 최신 상태 조회
- Delta Lake: 객체 스토리지 위에서 ACID, 스키마 관리, 버전 조회를 지원하는 테이블 계층

이 요소들은 모두 유용하지만 현재 프로젝트에서 동시에 도입할 필요는 없다. 각 기술은 실제 요구가 발생할 때 단계적으로 추가한다.

## 3. 최종 선택: 스트림 우선 하이브리드 아키텍처

이 프로젝트에는 순수 Lambda나 순수 Kappa보다 **스트림 우선 하이브리드 아키텍처**를 적용한다.

- 센서 신규 이벤트와 과거 재처리는 동일한 분석 코드로 처리한다.
- 원천 전력과 분석 결과는 S3 데이터 레이크에 보존한다.
- 가구별 루틴 통계와 학습 데이터 생성은 배치로 수행한다.
- 실시간 분석과 배치 분석이 공유하는 전처리·Window·피처 코드는 `nilm-core` 패키지로 단일화한다.
- 서비스 화면은 데이터 레이크를 직접 조회하지 않고 Redis와 PostgreSQL의 Serving View를 사용한다.

```text
                               ┌───────────────────────────────┐
ESP32 → MQTT → Kafka Raw ─────>│ Realtime Analysis            │
                               │ - 중복·순서 검사              │
S3 Replay → Kafka Replay ─────>│ - Window / Event Detection    │
                               │ - NILM / 패턴 변화 판단       │
                               └───────┬──────────────┬────────┘
                                       │              │
                                       ▼              ▼
                                Redis/PostgreSQL   S3 Silver/Gold
                                  Serving View           │
                                       │                 ▼
                                       │          Spark Batch / GPU
                                       │          루틴·학습·재평가
                                       ▼
                                Dashboard / Alert

Kafka Raw ── Archive Sink ──> S3 Bronze
외부 공개 데이터 ────────────> S3 Landing/Bronze
```

## 4. 데이터 레이크 계층

### 4.1 Landing

외부에서 받은 파일을 원형 그대로 임시 보관한다.

- AI-Hub·ENERTALK 등 공개 데이터
- 스마트플러그 정답 로그
- 수동 업로드한 CSV·JSON
- 공급처 메타데이터와 라이선스 문서

Landing 데이터는 분석 코드가 직접 참조하지 않는다. 검증을 통과한 데이터만 Bronze로 승격한다.

### 4.2 Bronze: 불변 원천

센서와 외부 데이터의 원본을 재처리 가능한 형태로 보존한다.

- 최대한 원본 의미를 유지한다.
- Append-only로 관리하고 기존 파일을 수정하지 않는다.
- 수신 시각, 원천 시각, 장치·가구 식별자, 순번과 스키마 버전을 반드시 기록한다.
- PostgreSQL 장애나 모델 변경과 무관하게 복구 가능한 기준 저장소로 사용한다.

### 4.3 Silver: 정제·표준화

분석과 학습이 공통으로 사용할 수 있도록 품질 처리를 수행한다.

- 중복 제거
- 시간대·타임스탬프 표준화
- 순번 누락과 데이터 공백 표시
- 비정상 측정값 격리
- 샘플링 주기 통일과 다운샘플링
- 단위·컬럼·스키마 표준화
- 전력 변화 이벤트와 가전 상태 이벤트 생성

Silver부터 Delta Lake 또는 Iceberg 같은 테이블 포맷 적용을 검토한다.

### 4.4 Gold: 목적별 데이터 제품

서비스, 분석, 모델 학습에 바로 사용할 데이터셋을 만든다.

- 가구별 일·주 단위 생활 루틴
- 가전별 사용 시각·횟수·지속 시간
- 이상 징후 점수와 판단 근거
- 학습·검증 Window
- 모델 평가 결과
- 대시보드용 집계 데이터

Gold 데이터는 하나의 거대한 테이블이 아니라 사용 목적별 데이터 제품으로 분리한다.

## 5. 데이터 경로와 저장 규칙

### 5.1 권장 경로

```text
s3://nilm-landing-{env}/
  aihub/dataset_version=.../...
  smartplug/dt=YYYY-MM-DD/...

s3://nilm-bronze-{env}/
  power_raw/dt=YYYY-MM-DD/hour=HH/bucket=NN/part-....parquet
  device_status/dt=YYYY-MM-DD/hour=HH/...

s3://nilm-silver-{env}/
  power_samples/dt=YYYY-MM-DD/hour=HH/bucket=NN/...
  appliance_events/dt=YYYY-MM-DD/bucket=NN/...
  quality_events/dt=YYYY-MM-DD/...

s3://nilm-gold-{env}/
  household_daily_profile/dt=YYYY-MM-DD/bucket=NN/...
  household_routine_baseline/version=.../...
  training_windows/dataset_version=.../appliance=.../...
  anomaly_features/dt=YYYY-MM-DD/bucket=NN/...

s3://nilm-artifacts-{env}/
  models/model_name=.../model_version=.../...
  preprocess/preprocess_version=.../...
  evaluation/model_version=.../...
```

### 5.2 파티셔닝 원칙

- 가구별 디렉터리를 최상위 파티션으로 만들지 않는다.
- 시간 범위 조회가 많으므로 `dt`와 `hour`를 우선 파티션으로 사용한다.
- 다가구 병렬 처리를 위해 `bucket = hash(household_id) % 64` 같은 고정 버킷을 사용한다.
- `household_id`는 컬럼으로 유지하고 필요한 경우 버킷을 함께 계산해 조회한다.
- 가구 수가 크게 늘어도 파티션 디렉터리 수가 가구 수만큼 증가하지 않게 한다.
- 파티션 값은 소문자와 `key=value` 형식을 사용한다.

### 5.3 파일 크기

- 센서 또는 가구별로 작은 파일을 직접 만들지 않는다.
- Archive Sink가 여러 가구의 데이터를 시간·버킷 단위로 모아 저장한다.
- 분석용 Parquet 파일은 약 128~512MB를 목표로 한다.
- 스트리밍으로 생성된 작은 파일은 정기 Compaction 작업으로 합친다.
- Kafka 메시지 수와 S3 파일 수를 줄이기 위해 ESP32에서 1초 단위 마이크로배치를 사용한다.

## 6. 핵심 테이블

| 계층 | 테이블 | 주요 내용 | 갱신 방식 |
|---|---|---|---|
| Bronze | `power_raw` | 장치가 보낸 원천 전력 샘플 | 스트리밍 Append |
| Bronze | `device_status` | 연결·해제·펌웨어·수집 상태 | 스트리밍 Append |
| Silver | `power_samples` | 정렬·중복 제거·단위 통일 샘플 | 스트리밍 또는 증분 배치 |
| Silver | `appliance_events` | 가전 ON/OFF와 신뢰도 | 스트리밍 Append/Upsert |
| Silver | `quality_events` | 누락·지연·이상값·스키마 오류 | 스트리밍 Append |
| Gold | `household_daily_profile` | 가구별 일간 가전 사용 통계 | 일 배치 |
| Gold | `household_routine_baseline` | 최근 기간 기반 정상 루틴 | 일 배치 Upsert |
| Gold | `anomaly_features` | 이상 판단용 피처와 근거 | 스트리밍·배치 결합 |
| Gold | `training_windows` | 모델 학습·검증 Window | 버전별 배치 생성 |
| Gold | `model_evaluation` | 모델·가전·가구별 성능 | 학습 후 생성 |

## 7. 이벤트와 스키마

### 7.1 원천 메시지 필수 필드

```json
{
  "event_id": "uuid",
  "household_id": "house-001",
  "device_id": "esp32-001",
  "device_timestamp": "2026-09-02T10:15:04.000Z",
  "received_at": "2026-09-02T10:15:04.120Z",
  "sequence": 182736,
  "schema_version": "power.raw.v1",
  "sample_rate_hz": 10,
  "samples": [
    {"offset_ms": 0, "active_power_w": 227.1}
  ]
}
```

### 7.2 분석 결과 필수 필드

- `event_id`
- `source_event_id` 또는 원천 Offset 범위
- `household_id`
- `appliance_type`
- `state`
- `confidence`
- `model_version`
- `preprocess_version`
- `rule_version`
- `window_start`, `window_end`
- `processed_at`

이 필드는 모델이 변경된 후에도 과거 판단을 재현하고 비교하기 위해 필요하다.

### 7.3 멱등성과 재처리

- 원천 중복 키: `device_id + sequence`
- 분석 이벤트 중복 키: 결정적 `event_id` 또는 `household_id + window + event_type + version`
- Kafka Consumer는 At-least-once를 기본으로 하고 저장소에서 중복을 제거한다.
- Replay는 원천 이벤트에 새 ID를 만들지 않고 `replay_run_id`만 추가한다.
- 재처리 결과는 기존 결과를 즉시 덮어쓰지 않고 `analysis_version`으로 구분한 뒤 검증 후 승격한다.

## 8. 실시간 처리와 Serving Layer

### 8.1 실시간 처리

```text
Kafka power.raw.v1
  → 스키마 검증
  → 중복·순서 검사
  → 가구별 Window
  → Event Detection
  → NILM 추론
  → 기준선 비교
  → analysis.snapshot.v1 / analysis.event.v1
```

현재 자원에서는 Spark Structured Streaming보다 가벼운 Python Kafka Consumer를 우선한다. Spark는 배치와 스트리밍 API를 통합할 수 있다는 장점이 있지만, EC2-B의 Kafka·PostgreSQL·실시간 분석과 메모리·CPU를 경쟁하게 된다.

향후 관리형 Spark 또는 별도 Worker 자원이 확보되면 Structured Streaming으로 이식할 수 있다. 이때 신규 스트림과 Replay 스트림이 동일 함수와 체크포인트 규칙을 사용하도록 한다.

### 8.2 Redis

Redis에는 영구 데이터가 아니라 즉시 조회가 필요한 Projection만 저장한다.

- 가구별 최신 총전력
- 현재 가전 ON/OFF 상태
- 최근 이상 징후 점수
- Dashboard용 짧은 시계열
- SSE/WebSocket 전송용 최신 상태

원천 데이터와 장기 이력은 Redis에 저장하지 않는다. Redis가 초기화되어도 Kafka 또는 PostgreSQL 이벤트를 다시 소비해 상태를 복원할 수 있어야 한다.

### 8.3 PostgreSQL

PostgreSQL에는 서비스 운영에 필요한 정형 데이터만 저장한다.

- 사용자·가구·기기 메타데이터
- 분석 이벤트 요약
- 알림 상태
- 확인·방문·조치 이력
- 모델·전처리 버전 메타데이터

고주파 원천 전력 샘플을 PostgreSQL에 전부 적재하지 않는다.

## 9. Delta Lake 적용 전략

블로그는 Delta Lake를 S3 위의 ACID 데이터 레이크로 소개한다. Delta Lake는 트랜잭션 로그를 이용해 스키마 검증, Upsert/Delete, 버전 조회, 스트리밍·배치 통합을 제공한다.

### 적용 권장 범위

- Bronze 원천: 단순 Append-only Parquet으로 시작 가능
- Silver 이벤트: 중복 제거와 수정이 필요하므로 Delta 적용 가치가 큼
- Gold 기준선: 일 배치 Upsert와 버전 비교가 필요하므로 Delta 적용 가치가 큼
- 학습 데이터: 데이터셋 버전 재현이 중요하므로 Delta Time Travel 또는 명시적 Dataset Version 사용

### 단계적 도입

1. MVP에서는 S3 + Parquet + 명시적 버전 경로로 시작한다.
2. 중복 보정, Upsert, 과거 Snapshot 조회 요구가 생기면 Silver부터 Delta를 도입한다.
3. 모든 Spark·조회 도구가 사용하는 Delta 프로토콜 버전을 지원하는지 확인한다.
4. `VACUUM`과 로그 보존 기간을 모델 재현 기간보다 짧게 설정하지 않는다.
5. 동시 Writer가 생기면 로컬 파일시스템이나 단일 EC2 디스크가 아니라 S3 같은 지원 저장소를 사용한다.

Delta Lake를 도입한다고 작은 파일 문제가 자동으로 모두 해결되는 것은 아니다. Compaction, 파티션 설계, 보존 정책은 별도로 운영해야 한다.

## 10. Kafka Connect와 Debezium 적용 판단

### Kafka Connect가 유용한 경우

- Kafka 원천을 S3에 표준 방식으로 내보낼 때
- 외부 데이터베이스나 파일 저장소와 반복적으로 연동할 때
- 커스텀 Consumer 코드를 줄이고 Connector 설정으로 운영하고 싶을 때

### Debezium이 유용한 경우

- 기기·가구·정책 마스터의 DB 변경을 분석 파이프라인에 실시간 반영해야 할 때
- 분석 결과가 아닌 DB 변경 이력을 데이터 레이크에 감사 목적으로 보존해야 할 때

### 현재 단계의 판단

- 센서 데이터는 MQTT–Kafka Bridge가 직접 생산하므로 Debezium이 필요하지 않다.
- 단일 S3 적재 경로만 필요하다면 가벼운 Raw Archive Consumer가 Kafka Connect보다 자원을 적게 쓸 수 있다.
- 연동 대상이 늘어나고 Connector를 2개 이상 운영할 때 Kafka Connect 도입을 검토한다.
- Debezium CDC를 원천 전력 처리와 같은 토픽에 섞지 않고 별도 `master.*` 토픽으로 분리한다.

## 11. 현재 자원 배치

| 위치 | 데이터 레이크 관련 역할 | 제외할 역할 |
|---|---|---|
| EC2-A | MQTT Broker, API, Monitoring, Redis, Dashboard | Spark, 원천 장기 저장, 모델 학습 |
| EC2-B | Kafka, Realtime Analysis, Raw Archive Sink, PostgreSQL, 제한적 Spark 배치 | 대규모 학습, 상시 Spark 클러스터 |
| 온프레미스 GPU | 학습, 대규모 오프라인 추론, 데이터셋 검증 | 외부 실시간 요청의 필수 경로 |
| t3.micro | WireGuard·Bastion 등 관리용 | Kafka, Redis, DB, Spark, DataNode |
| S3 | Landing/Bronze/Silver/Gold, 모델과 체크포인트 | 실시간 화면 직접 조회 |

현재 두 대 EC2로 HDFS를 운영 기준 저장소로 만들지 않는다. HDFS를 사용하더라도 교육·성능 비교용으로만 두고 S3를 재처리의 기준 저장소로 사용한다.

## 12. 파이프라인별 실행 주기

| 작업 | 주기 | 처리 방식 |
|---|---|---|
| 전력 수집·변화 탐지 | 1초 이하~수초 | Kafka Consumer 스트리밍 |
| Bronze Archive | 1~5분 파일 Rotation | 스트리밍 Sink |
| Silver 품질 보정 | 5분~1시간 | 증분 스트리밍 또는 Micro-batch |
| 작은 파일 Compaction | 시간·일 단위 | Spark Batch |
| 가구 루틴 기준선 | 일 1회 | Spark/Python Batch |
| 장기 통계 | 주·월 1회 | Batch |
| 모델 학습·검증 | 데이터 충족·모델 변경 시 | GPU Batch |
| 과거 Replay | 장애·모델 교체·검증 시 | S3 → Kafka Replay |

## 13. 장애와 복구

| 장애 | 복구 기준 |
|---|---|
| MQTT 연결 단절 | ESP32 `sequence`와 로컬 Ring Buffer로 재전송 |
| Kafka Consumer 장애 | Consumer Offset 이후 재시작, 저장 단계에서 멱등 처리 |
| Kafka 브로커 장애 | 센서 재전송과 S3 Archive를 안전망으로 사용. 운영 전 MSK 또는 다중 브로커 전환 |
| Redis 초기화 | Kafka 분석 이벤트 또는 PostgreSQL에서 Projection 재구성 |
| PostgreSQL 장애 | S3 백업/WAL 또는 관리형 DB 복원, 원천은 S3에 유지 |
| 잘못된 모델 배포 | 모델 버전 Rollback 후 해당 기간 S3 Replay |
| 잘못된 정제 결과 | Silver/Gold 버전 Rollback 또는 Bronze에서 재생성 |

## 14. 구현 단계

### Phase 1: 최소 데이터 레이크

- MQTT → Kafka → Realtime Analysis 완성
- Kafka → S3 Bronze Archive 구현
- S3 Parquet 경로와 스키마 버전 정의
- Redis 최신 상태와 PostgreSQL 이벤트 저장
- 특정 가구·기간 Replay 구현

### Phase 2: 정제·루틴 계층

- Silver 품질 처리와 결측·중복 지표
- Gold 일간 루틴과 이상 판단 피처 생성
- 작은 파일 Compaction
- 데이터·모델·전처리 버전 연결

### Phase 3: Lakehouse 확장

- Silver/Gold에 Delta Lake 도입
- Schema Enforcement와 Upsert 적용
- Time Travel 기반 학습 재현 검증
- Glue Catalog 또는 별도 메타데이터 카탈로그 연결

### Phase 4: 운영 확장

- Kafka를 MSK 또는 다중 브로커로 전환
- Spark 배치를 EMR Serverless 등 별도 자원으로 분리
- PostgreSQL을 RDS로 이전
- 가구 수와 처리량에 맞춰 Kafka 파티션·Consumer·S3 버킷 수 확장

## 15. 블로그 내용을 그대로 적용하지 않는 부분

1. **모든 데이터를 Kafka로 수집하지 않는다.** 공개 학습 파일과 모델 산출물은 S3 배치 적재가 더 적합하다.
2. **현재 실시간 처리를 반드시 Spark로 구현하지 않는다.** 현재 EC2 자원에서는 Python Consumer가 더 가볍다.
3. **Redis를 데이터 레이크로 사용하지 않는다.** Redis는 Serving Layer의 최신 상태 Projection이다.
4. **Delta Lake를 처음부터 전 계층에 적용하지 않는다.** 우선 Parquet으로 흐름을 완성한 뒤 수정·버전 관리가 필요한 Silver/Gold부터 도입한다.
5. **Lambda의 배치·실시간 로직을 이중 구현하지 않는다.** 공통 `nilm-core`와 Replay 경로로 처리 규칙을 단일화한다.
6. **Kafka를 영구 원천 저장소로 보지 않는다.** 재처리의 기준은 S3 Bronze다.

## 16. 완료 기준

- 신규 센서 데이터가 Kafka와 S3 Bronze에 모두 도착한다.
- 동일 가구 데이터의 순서가 유지되고 중복 메시지가 결과를 중복 생성하지 않는다.
- Bronze 데이터만으로 특정 가구·기간을 재처리할 수 있다.
- Redis를 비운 뒤 분석 이벤트에서 최신 상태를 복원할 수 있다.
- Gold 루틴 기준선에 입력 데이터 범위와 생성 버전이 기록된다.
- 모델 결과에 원천 Offset, 모델·전처리·규칙 버전이 연결된다.
- 잘못 생성된 Silver/Gold 데이터를 Bronze에서 다시 만들 수 있다.
- 파일 크기, Consumer Lag, 처리 지연, 결측률, 작은 파일 수를 모니터링한다.
