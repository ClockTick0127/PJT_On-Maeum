# NILM 자원 분산 전략 2안

> EC2 2대 + 온프레미스 GPU 서버 + 보조 인스턴스 1대라는 제약 안에서 "분산 파이프라인 아키텍처 증명"을 어디까지 할 수 있는지 판단하고, 분산 규모가 나오지 않는 부분은 어떤 대안으로 대체할지 정리한 문서. [NILM_아이디어_정리.md](NILM_아이디어_정리.md)의 MVP 범위와 [NILM_세가지_파이프라인_MSA_배치.md](NILM_세가지_파이프라인_MSA_배치.md)의 서버 배치를 전제로 한다.

## 1. 결론 요약

- MVP가 목표로 하는 **11가구·초당 110메시지** 규모의 분산 파이프라인 시연은 현재 자원으로 가능하다.
- "빅데이터"라 부를 수준의 실질적 분산(다수 워커 노드, HDFS 클러스터, 워커 8대 스케일 곡선 실험)은 현재 자원으로 불가능하다. 아이디어 정리 문서의 MVP 제외 항목과 리스크 폴백이 이미 이 한계를 반영하고 있으므로 방향은 유지한다.
- 분산 규모가 필요한 실험은 상시 인프라를 늘리지 않고 임시 자원(스팟 인스턴스, 온프레미스 서버 겸용)으로 분리한다.

### 이번 검토로 확정한 사항

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 인스턴스 계열 | **t3 계열 사용하지 않음** | 버스터블 인스턴스는 상시 스트리밍 부하에서 CPU 크레딧이 고갈되어 시연 중 성능이 급락할 수 있음 |
| 장기 저장소 | **MinIO 단일 노드** (HDFS 배제) | EC2 2대로는 HDFS 복제 3이 성립하지 않아 복제 없는 HDFS는 메모리만 소모함 |
| Kafka 메타데이터 관리 | **KRaft 단일 브로커** | ZooKeeper는 Kafka 4.0에서 제거됨. 별도 클러스터 없이 프로세스 1개로 기동 |
| 실시간 엔진 | **Flink** (실시간 탐지) + **Spark** (일 1회 배치) | 변화점 탐지는 건별 즉시 처리가 자연스럽고, Flink 최소 구성은 Spark Streaming 상시 구동보다 가볍거나 비슷함 |
| 고가용성 | MVP에서는 **미적용**, 로드맵 4단계로 이연 | EC2-B가 단일 장애점임을 수용. 실서비스 전환 시 필수 |

## 2. 전제 자원과 운영 제약

| 자원 | 핵심 사양/상태 | 권장 역할 |
| --- | --- | --- |
| EC2-A | 4 vCPU, RAM 약 15GiB, 디스크 약 309GB (비버스터블 계열로 변경 예정) | 외부 진입, 웹·API·MQTT·대시보드 |
| EC2-B | 4 vCPU, RAM 약 15GiB, 디스크 약 309GB (비버스터블 계열로 변경 예정) | Kafka, 실시간 분석, DB, 제한적 Spark 배치 |
| 온프레미스 GPU 서버 | 세부 사양 미확인 | NILM 모델 학습·검증·대규모 오프라인 추론, 필요 시 임시 워커 |
| 보조 EC2 | 1 vCPU, RAM 약 1GB, 여유 디스크 약 2.6GB | WireGuard 또는 관리용 점프 호스트로 제한 |

## 3. 현재 자원으로 가능한 것과 불가능한 것

### 가능한 범위 (완료 기준 대비)

- 초당 110개 메시지는 Kafka 기준으로 매우 작은 부하다. 단일 브로커로 유실 0건, 5초 이내 표시 목표를 달성할 수 있다.
- "2개 워커의 작업 분산 확인"(완료 기준 4번)은 EC2-B 안에서 워커 컨테이너 2개를 띄우는 **논리적 분산**으로 충족한다. 증명하려는 것은 가구 키 파티셔닝 → 파티션별 병렬 처리라는 구조이므로 물리 노드 수와 무관하게 성립한다.
- 디스크 309GB면 11가구 Parquet 장기 적재는 수개월 이상 충분하다.

### 불가능하거나 위험한 범위

1. **HDFS 클러스터.** NameNode 1대 + DataNode 3대, 즉 EC2 최소 4대가 필요하다. 2대에서는 복제가 성립하지 않는다. (상세는 5.1절)
2. **Kafka·DB 고가용성.** 단일 브로커(복제본 1), 단일 DB이므로 EC2-B가 멈추면 수집·분석·저장이 모두 멈춘다. MVP에서는 수용한다.
3. **워커 다수 스케일 곡선 실험.** 상시 인프라로는 불가능하므로 4절의 임시 자원 전략으로 분리한다.
4. **보조 EC2 활용.** RAM 1GB, 디스크 2.6GB로 Kafka·DB·Spark·MQTT 브로커 어느 것도 올릴 수 없다.

### EC2-B 메모리 예산 (15GiB 기준)

| 구성요소 | 할당 | 비고 |
| --- | --- | --- |
| Kafka (KRaft) | 2GB | 힙 + 페이지 캐시 여유 |
| Flink JobManager | 1GB | 작업 조율 |
| Flink TaskManager | 2~3GB | 실제 처리, 1~2개 |
| Spark (배치 시간에만 기동) | 3~4GB | 상시 상주 금지, 일 1회만 |
| Redis | 0.5GB | 최신 상태 저장 |
| PostgreSQL | 1.5GB | 루틴·이벤트·알림 이력 |
| MinIO | 1GB | Parquet 장기 저장 |
| OS 및 여유 | 2GB | |
| **합계** | **약 13~15GB** | 컨테이너별 메모리 상한 필수 |

Flink와 Spark를 동시에 상주시키면 예산을 초과한다. Spark는 배치 시간대에만 띄우고 종료하는 방식으로 공존시킨다.

## 4. 분산 규모가 나오지 않을 때의 대안 (우선순위 순)

### 1순위: 논리적 분산으로 현 자원 안에서 완결

- 실시간 탐지는 Flink(또는 폴백으로 Python Kafka Consumer 컨슈머 그룹)로 운영하고, Spark는 일 1회 배치에만 사용한다.
- 가구 키 파티셔닝과 파티션별 병렬 처리(Flink 병렬도 2 또는 컨슈머 그룹 리밸런싱)로 "분산 처리 구조"를 증명한다.
- 상시 스트리밍 엔진을 하나로 줄여 메모리 압박을 해소한다.

### 2순위: 물리 2노드 분산 데모

- "노드 간 분산"을 직접 보여야 할 때 EC2-A에 워커(Flink TaskManager 또는 Spark 워커) 1개를 추가로 배치해 A·B 2노드 클러스터를 구성한다.
- EC2-A는 웹·API·MQTT를 담당하므로 워커 메모리를 3~4GB로 제한하고 시연 시간대에만 기동한다.

### 3순위: 스케일 실험만 임시 자원으로 분리

상시 인프라를 늘리지 않고 실험 결과(처리량·지연 그래프)만 남기는 방식이다.

| 방법 | 내용 | 비고 |
| --- | --- | --- |
| 스팟 인스턴스 | m5.large급 스팟 4~8대를 몇 시간 빌려 스케일 곡선 측정 후 반납 | 수 시간 기준 수 달러 수준 |
| 온프레미스 GPU 서버 겸용 | 보조 EC2의 WireGuard로 연결해 학습 외 시간에 워커로 활용 | VPN 경유 셔플 트래픽 지연 감안 |
| EMR Serverless | Parquet 배치만 서버리스로 처리 | 분산 시스템을 직접 구축·운영해보는 학습 목표와는 거리가 있어 후순위 |

## 5. 검토 과정에서 정리한 개념

### 5.1 HDFS 클러스터와 "노드"

**노드는 서버(컴퓨터) 1대**를 뜻한다. "노드로 나눈다"는 것은 하나의 저장소처럼 보이는 시스템을 실제로는 여러 서버가 나눠 담당한다는 의미다.

```text
                [NameNode]  ← "목차" 담당 서버 1대 (메타데이터만 보유)
                     │
        ┌────────────┼────────────┐
   [DataNode A]  [DataNode B]  [DataNode C]   ← 실제 블록을 디스크에 저장
    블록1 사본     블록1 사본     블록2 사본
    블록2 사본     블록2 사본
```

- 파일은 128MB 단위 블록으로 쪼개지고, 각 블록은 기본 3개 서버에 복제된다(`dfs.replication = 3`). 그래서 "최소 3노드"가 권장된다.
- EC2 관점의 구성은 같은 VPC·서브넷에 EC2 4대를 띄우고 각 서버에 Hadoop을 설치한 뒤 역할별 프로세스를 켜는 것이다. `fs.defaultFS`로 NameNode 주소를 모든 서버에 공통 지정하고, `workers` 파일에 DataNode 서버 목록을 적고, 보안 그룹에서 Hadoop 포트(8020, 9866, 9870 등)를 서버 간에 연다.
- **어느 블록을 어느 서버에 둘지는 사람이 정하지 않는다.** Spark가 파일을 쓰면 NameNode가 대상 서버 목록을 정하고, 첫 DataNode가 받으면서 다음 DataNode로 넘기는 파이프라인 복제가 자동으로 일어난다. 서버가 죽으면 NameNode가 감지하고 남은 사본으로부터 복제본 수를 자동 회복한다.
- 한 서버에 DataNode 컨테이너 3개를 띄우는 것은 같은 물리 디스크에 저장하므로 서버 장애 대비라는 복제의 목적을 달성하지 못한다. 동작 원리 학습용으로만 의미가 있다.
- MinIO는 단일 프로세스로 뜨고 Spark에서는 `s3a://` 경로만 바뀐다. EC2 2대에서는 HDFS를 올려도 복제가 안 되므로 잃는 것 없이 메모리와 운영 복잡도만 줄어든다. 이후 다중 서버 저장이 필요해지면 API가 같은 AWS S3로 코드 수정 없이 이전할 수 있다.

### 5.2 ZooKeeper와 KRaft

- **ZooKeeper**는 분산 시스템의 합의 정보(브로커 리더 선출, 생존 브로커 목록, 토픽 설정 등)를 대신 보관·중재하는 별도 프로그램이다. Kafka를 쓰려면 완전히 별개의 ZooKeeper 클러스터를 하나 더 운영해야 했다.
- **KRaft**(Kafka Raft)는 그 관리 기능을 Kafka 내부에 내장한 방식이다. Kafka 2.8에 도입되어 현재 기본이고, ZooKeeper 방식은 Kafka 4.0에서 제거되었다. 새로 구축하는 프로젝트는 KRaft 단일 브로커로 시작하면 된다.

### 5.3 Flink와 Spark Structured Streaming의 차이

| 구분 | Spark Structured Streaming | Flink |
| --- | --- | --- |
| 처리 단위 | 몇 초 단위 마이크로배치 | 이벤트 도착 즉시 건별 처리 |
| 지연 | 트리거 간격만큼 발생 | 매우 낮음 |
| 최소 구성 | 마스터 + 워커 상시 상주 | JobManager(약 1GB) + TaskManager(2~3GB) |
| 적합 용도 | 배치와 코드 공유, 집계 중심 | 변화점 탐지처럼 "지금 켜졌다"를 즉시 알아야 하는 용도 |

이 프로젝트의 핵심이 실시간 이벤트 탐지이므로 아이디어 정리 문서의 의사결정 3번은 "실시간 Flink + 배치 Spark"로 닫는다.

### 5.4 고가용성(High Availability)

- 구성 요소 일부가 죽어도 서비스 전체는 계속 동작하게 만드는 성질이다. 그것 하나가 죽으면 전체가 멈추는 지점을 **단일 장애점(SPOF)** 이라 하고, 고가용성은 이를 복제로 없애는 설계다.
- 예: Kafka 브로커 3대 + 복제본 3, PostgreSQL 주-대기 복제, 동일 서비스 2대 + 로드밸런서.
- 현재 구성은 Kafka·DB·분석이 모두 EC2-B 위에 있어 **EC2-B 자체가 단일 장애점**이다. 서버 수를 늘려 복제해야 해소되므로 MVP에서는 수용하고, 실제 돌봄 서비스로 운영할 때는 알림 중단 자체가 위험이므로 필수 과제가 된다.

## 7. 남은 확인 사항

1. EC2 인스턴스 계열 확정(m5/m6i 등)과 그에 따른 메모리 예산 재산정
