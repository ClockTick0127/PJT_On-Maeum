# 모니터링 서비스 진행 현황 및 HDFS·배치·위험 평가 개발 계획

- 작성일: 2026-09-18
- 확인 범위: 현재 저장소의 monitoring-service, realtime-analysis-service, HDFS loader 구현
- 목적: 구현된 기능과 앞으로 개발할 기능을 구분하고, 위험 점수 계산·일일 집계·리포트의 책임과 연결 순서를 정리한다.
- 확인 수준: 소스 코드 및 테스트 파일 확인. 이번 문서 작성 과정에서 서비스를 실행하거나 테스트를 재실행하지 않았으므로 운영 배포·통합 검증 완료를 의미하지 않는다.
- 이 문서의 신규 서비스명·테이블명·메시지명은 별도 표시가 없으면 설계 제안이다. 서비스 코드는 변경하지 않았다.

## 1. 현재 상태 요약

모니터링에는 분석 이벤트 수신, 이벤트 저장, 입력 점수의 위험 등급 분류, 안전 확인 알림, 응답·만료 처리, 대시보드·SSE, 스냅샷 기반 마지막 활동 반영이 구현돼 있다.

다만 **모니터링이 이벤트 근거로 위험 점수를 직접 계산하는 기능은 아직 구현되지 않았다.** 현재는 메시지에 들어온 `score`를 대상자 상태에 반영하고 주의·위험 임계치로 등급을 나눈다.

분석 서비스는 이미 `score` 없는 새 이벤트 계약을 사용하므로, **분석 생산자와 모니터링 소비자의 계약 불일치를 먼저 해결해야 한다.** HDFS 도입·확장과 일일 배치 분리는 이 계약 전환과 연결하되, 실시간 위험 계산이 HDFS 배치 완료를 기다리게 만들지는 않는다.

## 2. 모니터링 서비스에서 구현된 사항

| 영역 | 현재 구현 | 범위·제약 |
| --- | --- | --- |
| 분석 이벤트 수신 | `analysis.event.v1` 소비, JSON 역직렬화, 필수값·점수 범위 검사 | 현재는 입력 `score` 필수 |
| 중복 처리 방지 | 가구의 대상자를 잠금 조회하고 `event_id`가 이미 있으면 종료 | 이벤트 재수신에 따른 추가 알림 방지 |
| 이벤트 저장 | 이벤트 유형, 가구, 발생 시각, reason, 점수·등급·정책 식별자 저장 | 가전 유형은 현재 최상위 `appliance_type`을 읽음 |
| 위험 등급 분류 | 기본 70 이상 WARNING, 90 이상 DANGER | 이벤트 조합·지속시간 기반 점수 계산은 미구현 |
| 안전 확인 알림 | 이벤트 저장과 알림 생성을 같은 트랜잭션에서 처리 | 현재 별도 Incident 엔터티·수명주기 구현은 확인되지 않음 |
| Web Push | 구독 등록, 커밋 이후 발송, 발송 결과 저장 | 푸시 비활성화 지원. 커밋 후 유실·실패의 지속적 자동 재발송은 미구현 |
| 응답·만료 | 수신자 본인 확인, 동일 응답 재전송 허용, 다른 응답 충돌 처리, 30초 응답 기한 및 만료 처리 | 30초는 알림 생성 기준. 응답 처리가 위험 점수 재계산을 수행하지는 않음 |
| 외출 모드 | 즉시·예약 외출 상태 반영, 시작·종료 스케줄 처리 | 이벤트 발생 당시 외출 여부와 모니터링 활성 여부에 따라 알림 억제 |
| 스냅샷 수신 | `analysis.snapshot.v1` 소비, 가전 상태 저장, ON→OFF로 마지막 활동 갱신 | 첫 스냅샷은 초기 상태로 처리. 확정 사용 세션 전체를 복제하는 기능은 아님 |
| 대시보드·조회 | 담당자·본인 대시보드, 대상자 검색·등록, 이벤트 이력, 담당자 프로필 변경 API | 대상자 본인 또는 배정 담당자의 조회 권한 확인 |
| SSE | 상태 변경 커밋 후 대상자 상태를 다시 읽어 배정 담당자에게 전송, heartbeat | 현재 애플리케이션 이벤트·프로세스 내부 연결 관리. 내구성 있는 Kafka 상태 이력 발행과 다름 |
| 시간별 전력 그래프 | 전체·가전별 시간별 전력량 테이블과 하루 24개 구간 조회 API | 조회 구현이며 실제 집계값을 채우는 운영 적재 경로는 별도 연결 필요 |
| 개발 검증 기반 | 이벤트·푸시·외출·대시보드·SSE·스냅샷·전력 조회 등 테스트 파일 존재 | 이번 문서 작성에서는 실행 결과를 새로 검증하지 않음 |

현재 알림 수신자는 대상자의 `auth_sub`로 연결된다. 이를 모든 보호자·담당자에게 전달하는 정책이 이미 구현됐다고 해석하지 않는다. 수신자 확대·전파 정책은 별도 확정이 필요하다.

## 3. 먼저 해결할 계약 차이

### 3.1 점수 없는 이벤트와 기존 소비자 충돌

- 분석 `AnalysisEvent`: `event_id`, `household_id`, `event_type`, `occurred_at`, `reason`. `score` 없음.
- 모니터링 `AnalysisEventMessage`: `score` 필드가 존재하고 서비스 검증에서 null을 거부.
- 현재 오류 처리기는 소비 컨테이너를 중지하는 방식이므로 새 계약 메시지가 처리 실패를 일으킬 수 있다.
- 전환 방향: 입력 점수 의존을 제거하고, 이벤트 검증·저장 후 모니터링 내부 평가 결과로 점수와 등급을 계산한다.
- 기존 DB의 점수 컬럼은 삭제를 전제로 하지 않는다. 입력 점수와 계산 결과의 의미를 정리하고 이력·마이그레이션 호환 방식을 결정한다.

### 3.2 가전 유형 위치

- 새 분석 계약은 `reason.appliance_type`을 사용한다.
- 현재 모니터링 DTO·저장은 최상위 `appliance_type`을 참조한다.
- reason에서 추출·검증하도록 맞추고, 전환 중 기존 계약 수용 여부를 정한다.

### 3.3 이벤트 분류와 추가 토픽

| 입력 | 목표 처리 | 현재 모니터링 상태 |
| --- | --- | --- |
| ROUTINE_MISSED | 위험 평가 입력 | 이벤트 소비 기반은 있으나 새 계약·유형별 평가 필요 |
| PROLONGED_INACTIVITY | 위험 평가 입력 | 동일 |
| PROLONGED_APPLIANCE_USE | 위험 평가 입력 | 동일 |
| ROUTINE_CHANGED | 정보성 이력·그래프, 위험 점수 미반영 | 정보성 분기 필요 |
| analysis.activity.v1 | 일일 활동지수 저장 후 위험 기여도 계산 | 전용 소비자·저장 경로 확인되지 않음 |
| analysis.data-quality.v1 | DATA_GAP/RECOVERED 상태 반영, 결측을 위험으로 오해하지 않도록 제어 | 전용 소비자·저장 경로 확인되지 않음 |
| analysis.snapshot.v1 | 현재 상태·마지막 활동 표시 | 소비 구현 있음 |

`activity_index`는 현재 개인의 평소 대비 상대 지수가 아니라 고정 목표값으로 계산한 일일 절대 지수다. 위험 계산 정책을 정할 때 이 의미를 기준으로 삼는다. `INSUFFICIENT_DATA`의 null을 0점으로 치환하지 않는다.

## 4. 분석 서비스와 HDFS의 현재 구현

### 4.1 실시간 분석

- 추론·확정 ON/OFF 판정 후 사용 세션과 일일 관측을 DB에 저장한다.
- 위험 이벤트 3종은 입력 측정값 처리 중 가구별 공통 간격으로 평가한다. 초기 정책은 60초이며 활성 정책의 최소 평가 간격을 사용한다.
- 기대 시각까지 사용 없음, 마지막 사용 종료 이후 미활동, 열린 사용 세션의 허용시간 초과를 각각 검사한다.
- 데이터가 끊기면 측정값 기반 위험 평가는 호출되지 않는다. 별도 품질 감시가 DATA_GAP과 복구를 처리한다.
- 사용 세션 변경을 HDFS로 내보내는 전용 변경 메시지 경로는 추가 설계·구현 대상이다. 스냅샷을 사용 세션 메시지로 간주하지 않는다.

### 4.2 일일 배치

현재 일일 스케줄러는 분석 서비스 프로세스 내부 스레드다. 기본 한국 시간 00:10을 기준으로 전날 작업을 수행하며 다음 순서로 연결돼 있다.

1. 일일 관측 마감·품질 확정
2. 일일 활동지수 계산·발행
3. 최근 7일과 이전 21일의 최초 사용 시각 비교 → ROUTINE_CHANGED
4. 최근 28일 중 VALID 관측일로 기준선 계산·DB 갱신·실행 프로세스 캐시 갱신

기준선은 기본 유효 표본 14일 이상에서 계산한다. `normal_days=active_days`, `window_days=sample_days`이며 적격 요일별 프로필이 있으면 해당 값을 사용한다. `window_days`가 항상 달력상 28일인 것은 아니다.

활동지수는 사용 횟수 점수 50%, 가전 다양성 30%, 사용 시간 20%를 반영한다. 관측 부족일은 null로 발행한다.

현재 실행 날짜·중복 억제 상태는 메모리에 있으므로 컨테이너 증설·재시작을 고려한 공용 실행 이력과 잠금이 필요하다. 전체 과거 누락 날짜를 자동 순회하는 백필 기능과도 구분한다.

### 4.3 HDFS 원천 보관

- `infrastructure/hdfs/docker-compose.yml`: NameNode, DataNode, loader 구성 존재.
- loader는 `power.raw.v1`을 별도 소비 그룹으로 읽고 Bronze Parquet로 적재한다.
- 원본 payload와 Kafka topic/partition/offset, 측정·수신 관련 시각을 보관한다.
- 파싱 오류는 quarantine에 보관하며, 기본 5분 또는 50,000건 조건으로 flush한다.
- 파일과 offset 범위를 담은 manifest를 기록한 뒤 Kafka offset을 커밋한다.
- 경로는 UTC 적재일 기준이므로 한국 시간의 측정일별 마감과 구분해야 한다.
- 이 구현만으로 Silver/Gold 생성, 분석 완료 대조, end-to-end exactly-once, 운영 적재 검증이 완료됐다는 뜻은 아니다.

## 5. 목표 책임 분리

| 주체 | 책임 | 다른 주체와의 연결 |
| --- | --- | --- |
| 실시간 분석 | 전력 추론, 확정 사용 세션, 패턴 탐지 근거 발행 | 기준선은 DB/캐시에서 읽고 최종 위험 점수는 계산하지 않음 |
| 모니터링 | 현재 위험 점수·등급, 사건·알림·응답, 화면 상태 | 분석 이벤트·활동지수·품질 상태를 입력으로 사용 |
| 배치 실행 서비스 | 마감, 활동 집계, 루틴 변화, 기준선, 위험 이력 요약, 리포트 | 날짜·버전별 작업 순서와 재시도 관리 |
| HDFS | 원천 및 상세 이력 보관, 확정 집계·리포트 데이터 제공 | 실시간 위험 판정의 매 요청 조회 저장소로 사용하지 않음 |

```text
Kafka 원본 전력 ──→ 실시간 분석 N개 ──→ 패턴 이벤트 ──→ 모니터링
      │                   │                            │
      │                   └─ 확정 사용 세션 이력        └─ 위험·사건·조치 변경 이력
      └──────────────────────────┬─────────────────────┘
                                 ↓
                       HDFS Bronze → Silver
                                 ↓
              배치 실행권 확보 → 입력 완료 확인 → 날짜 마감
                                 ↓
          활동 집계·루틴 변화 → 기준선 계산·활성화 → 리포트 데이터·문서
                    │                 │
                    ↓                 ↓
              모니터링 조회 DB    analysis_db → 분석 인스턴스 캐시
```

위 그림의 사용 세션·모니터링 변경 이력 외부 전송, Silver/Gold, 리포트 경로는 앞으로 구현할 영역이다.

## 6. 앞으로 진행할 사항

### 6.1 모니터링 위험 점수 평가

1. 새 이벤트 DTO와 유형별 reason 검증을 적용한다. 미등록 유형·잘못된 메시지의 오류 처리 정책도 확정한다.
2. 활동지수·데이터 품질 소비자와 저장 모델을 추가한다. 메시지 ID 중복, 늦은 메시지, 배치 재계산 버전을 처리한다.
3. 위험 평가 로직을 별도 컴포넌트로 분리한다. 이벤트 기본 기여도, 지속 시간, 동시 발생, 활동지수, 외출·품질 상태를 입력으로 사용한다.
4. 점수 계산식·가중치·평가 구간·임계값·상한·감쇠·해소 정책을 확정하고 정책 버전을 저장한다. 수치는 아직 확정하지 않는다.
5. 같은 원인의 여러 이벤트를 단순 합산하지 않도록 중복 기여도 제한을 둔다. 장시간 가전 사용과 활동지수 상승이 서로 위험을 상쇄할지도 명시한다.
6. 일일 활동지수는 전날 요약이다. 수신 순간의 현재 활동으로 해석하지 않고 대상 날짜·유효기간을 평가에 반영한다.
7. DATA_GAP 자체는 위험 가점으로 사용하지 않는다. 활동 기반 판단 가능 여부와 기존 위험 사건 유지·해소 여부를 분리한다.
8. 정보성 ROUTINE_CHANGED는 저장·표시에 사용하며 위험 점수·위험 알림 생성 경로에서 제외한다.
9. 신규 이벤트뿐 아니라 해소·외출 전환·품질 복구·시간 경과 때도 재평가할 조건을 정한다. 위험 해소 근거를 스냅샷/별도 해소 계약 중 무엇으로 받을지 결정한다.
10. 평가 결과와 근거 이벤트 ID, 활동지수 버전, 정책 버전, 적용 시각을 저장하고 SSE에 반영한다.

### 6.2 사건 및 이력

- 현재 notifications 중심 흐름과 독립적인 Incident 모델 도입 여부를 확정한다.
- 도입 시 사건 생성·병합·확인·종료 조건, 중복 알림 제한, 담당자·대상자 등 수신자 정책을 정의한다.
- 최신 상태와 별개로 위험 점수 변경, 사건 상태 변경, 알림 발송·응답·조치 이력을 누적 저장한다.
- HDFS 전송은 DB 변경과 함께 outbox를 기록하거나 CDC로 전달하는 방식 중 하나를 선정한다. Spring 내부 이벤트/SSE를 영구 감사 이력으로 대체하지 않는다.
- 전송 실패 후 재시도와 수신 측 중복 제거를 구현한다. 리포트에는 하루 최대 위험 점수, 위험 지속 시간, 사건 수, 대응 시간을 재현할 수 있어야 한다.

### 6.3 일일 배치 실행 주체 분리

- 실시간 분석 진입점에서 DailyActivityIndexScheduler 시작을 제거하고 배치 전용 진입점으로 이동한다.
- 초기에는 같은 이미지의 다른 실행 명령을 사용할 수 있다. 별도 저장소 분리는 필수가 아니다.
- 단일 스케줄러와 DB 실행 잠금·영구 실행 이력을 함께 사용한다. 컨테이너 수 1만으로 재시작·수동 실행 중복을 해결하지 않는다.
- 날짜·버전·단계별 PENDING/RUNNING/SUCCEEDED/FAILED 상태, 시도 횟수, 오류, 입출력 버전을 저장한다.
- 날짜 지정 실행, 실패 단계 재시도, 누락 날짜 백필을 지원한다. 전체 파이프라인을 하나의 긴 DB 트랜잭션으로 묶지 않는다.
- 기준선 갱신 후 각 실시간 인스턴스가 활성 버전을 확인하고 캐시를 갱신하도록 한다.
- 활동지수·이벤트 발행도 outbox/멱등 저장 등으로 재실행 중복과 발행 유실을 처리한다.

### 6.4 HDFS 집계 계층

| 계층 | 제안 데이터 | 저장 목적 |
| --- | --- | --- |
| Bronze | 원본 전력, 사용 세션 변경 원문, 분석 이벤트, 모니터링 상태 변경 원문 | 재처리·추적 |
| Silver | 중복 제거·시간 정규화한 전력, 확정 사용 세션, 사건·위험·조치 상세 이력 | 집계 기준 사실 데이터 |
| Gold | 일일 관측 품질·가전 활동·전력량, 기준선 버전, 일일 위험 요약, 리포트 결합 결과 | 분석·조회·리포트 |

- 사용 세션은 `session_id`와 변경 버전으로 시작/종료/정정 기록을 연결한다. 분석 결과에 모델·판정 알고리즘 버전을 남긴다.
- 스냅샷의 가전 ON/OFF만으로 가전별 전력량을 정확히 산출할 수 없다. 가전별 Wh 그래프에는 분해 전력 시계열 또는 별도 추정 계약이 필요하다.
- Bronze 저장 완료와 추론 결과 저장 완료를 각각 확인한다. 원본 전력만 있다고 현재 기준선 계산에 필요한 확정 세션이 준비된 것은 아니다.
- 마감 대상의 측정일, 시간대, 파티션별 입력 범위, manifest, 지연 허용 시간을 고정한다. offset은 도착 범위의 기준이며 측정일 판별은 측정 시각으로 수행한다.
- 늦은 입력은 마감 결과를 무단 덮어쓰지 않고 재계산 버전·정정 정책으로 처리한다.
- Gold 기준선은 버전 이력으로 보관하고, 검증 후 활성 버전만 analysis_db에 제공한다. 과거 날짜 재처리가 현재 활성 기준선을 역행시키지 않도록 한다.
- 그래프용 집계는 모니터링의 조회 테이블에 공급한다. HDFS에 저장했다는 사실만으로 기존 API의 데이터가 채워지지는 않는다.

### 6.5 자동 리포트

- 일일 마감 결과, 활동지수, 위험·사건·조치 요약, 기준선 버전을 결합한 리포트 입력을 만든다.
- 당일 탐지에 사용한 기준선과 배치에서 새로 계산한 기준선을 구분한다.
- 데이터 부족일은 정상/활동 0으로 표현하지 않고 관측 불충분으로 표시한다.
- 입력 버전과 생성 결과를 저장해 재생성 가능하게 한다. 리포트 실패는 이미 성공한 기준선 계산과 분리해 재시도한다.
- 리포트 생성·보관과 외부 발송을 별도 단계로 둔다. 수신자·발송 주기·동의 범위는 추후 결정한다.

## 7. 권장 진행 순서와 완료 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 이벤트 계약 정합성 | 점수 없는 실제 분석 메시지가 저장되고 가전 유형이 보존됨. 기존 계약 전환 전략 검증 |
| 2 | 활동지수·품질 수신 | VALID/null, GAP/RECOVERED, 중복·역순·재계산 버전 테스트 통과 |
| 3 | 모니터링 위험 평가 | 정책별 계산·근거 이력 저장, 정보성 이벤트 제외, 외출·결측·해소 동작 검증 |
| 4 | 사건·알림 연동 | 필요한 경우 Incident 수명주기 추가, 응답·만료·중복 알림·재발송 검증 |
| 5 | 배치 실행 분리 | 분석 컨테이너를 늘려도 날짜별 배치 실행권은 하나. 재시작·실패 단계 재실행 가능 |
| 6 | 원천·상세 이력 수집 확대 | 원천 manifest와 분석 처리 범위 확인, 세션·모니터링 변경 이력 수집 |
| 7 | Silver/Gold·조회 공급 | 정제·마감·재계산 버전, 기준선 활성화·전체 인스턴스 갱신, 그래프 적재 검증 |
| 8 | 리포트 | 동일 입력 버전 추적, 결측 표시, 생성 실패 단독 재시도 검증 |

계약·모니터링 평가와 배치 분리·HDFS 준비는 인터페이스 합의 후 병행 가능하다. 최종 통합 검증에는 Kafka 재전송, 서버 재시작, 다중 컨테이너, 지연 데이터, 공백·복구, 배치 중간 실패를 포함한다.
