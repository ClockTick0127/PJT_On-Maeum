# 3. HDFS, Spark 성능 및 네트워크 병목 해결

## 3-1. 목표

- 이전 구조의 전체 처리시간 추가 단축
- 압축 해제, 변환, HDFS 업로드의 동시 처리 검토
- HDFS 상태 오류와 불필요한 재작업 방지
- 팀원 노트북 사용 가능 시간이 짧은 환경에 맞게 구조 개선

## 3-2. 추가로 발견된 문제와 대응

| 문제                 | 원인/상황                                               | 대응                                                   |
| -------------------- | ------------------------------------------------------- | ------------------------------------------------------ |
| HDFS 장애 시 재처리  | NameNode 연결 실패를 “완료 데이터 없음”으로 잘못 판단   | 작업 시작 전 HDFS 상태 확인, 비정상 시 작업 중단       |
| master DataNode 혼선 | 중지한 `master-ss` DataNode가 잠시 저장 대상으로 인식됨 | master는 NameNode만 사용, worker 4대만 DataNode로 고정 |
| 병렬 처리 성능 저하  | 압축 해제와 Parquet 변환이 동시에 로컬 저장 장치를 사용 | 두 작업은 순차 처리하고 HDFS 업로드만 병렬 처리        |
| 메모리 사용 영향     | 다른 프로그램의 메모리 사용량이 높을 때 변환 속도 저하  | master의 메모리 사용량을 줄이고 재측정                 |

## 3-3. 성능 확인

### 처리 구조

```text
로컬: 압축 해제 → Parquet 변환
                     │
                     └─ 이전 채널 HDFS 업로드와 병렬
```

### 측정 결과

| 항목              |    이전 | 개선 후 |
| ----------------- | ------: | ------: |
| 5채널 총 실행시간 |   6.7분 |   4.9분 |
| Parquet 변환 평균 | 0.522분 | 0.442분 |
| 로컬 처리 평균    | 0.910분 | 0.738분 |

- 메모리 여유 확보 후 로컬 처리 속도가 개선됨
- 단, 서로 다른 채널을 비교한 결과이므로 전체 개선 폭을 모두 메모리 효과로 보기는 어려움

## 3-4. Parquet 압축률 재계산

10개 고유 채널 기준:

```text
원본 CSV   약 55.25GiB
Parquet    약 4.12GiB
```

- 평균 압축률: 약 **7.46%**
- 전체 5.8TB 적용 시 30Hz Parquet 예상 크기: 약 **433GB**

# 4. 현재 검토 중인 방향: 1Hz 사전 축소

## 4-1. 배경

30Hz Parquet으로 줄여도 약 433GB가 예상되어 HDFS 저장 시간이 여전히 부담됨.

## 4-2. 변경안

```text
30Hz 원본
→ 로컬 압축 해제
→ 1Hz로 축소
→ Parquet 저장
→ 로컬에 미리 보관
→ worker 준비 시 HDFS 저장
```

## 4-3. 예상 효과

| 항목              |    30Hz 기준 |         1Hz 단순 추정 |
| ----------------- | -----------: | --------------------: |
| Parquet 전체 용량 |     약 433GB |             약 14.4GB |
| HDFS 전송 시간    | 수 시간 이상 |     수십 분 수준 예상 |
| worker 필요 시간  |       장시간 | HDFS 업로드 시간 중심 |

### 기대 효과

- HDFS 전송량 대폭 감소
- worker 4대를 오래 켜둘 필요 감소
- HDFS 복제 수를 2 이상으로 높일 여지 확보
- Spark는 이후 전체 데이터 검사, 채널 정렬, 결합 등에 집중 가능

### 한계

- 1Hz로 줄여도 5.8TB 원본은 한 번 모두 읽어야 함
- 압축 해제와 변환은 여전히 `master-ss` 성능에 의존
- 1Hz 데이터는 단일 PC에서도 처리 가능하므로, Spark 사용 목적을 명확히 설명할 필요가 있음

# 5. 현재 판단

- 초기 구조의 가장 큰 문제는 **네트워크 전송량**이었음
- 이를 줄이기 위해 전처리 위치를 HDFS 앞단으로 이동
- 이후 실제 실행 과정에서 HDFS 상태 확인, DataNode 구성, 병렬 처리 방식까지 수정
- 현재는 **30Hz 전체를 HDFS에 저장하는 방식보다, 1Hz로 축소한 뒤 분산 저장하는 방향이 더 현실적**이라고 판단

### 역할 구분

```text
master-ss
→ 원본 압축 해제
→ 1Hz 축소
→ Parquet 생성

HDFS
→ 분산 저장
→ 복제 및 공유 저장

Spark
→ 전체 데이터 검사
→ 채널 정렬/결합
→ 학습용 데이터 생성
```

# 7. 추가 진행

## 7-1. CSV → Parquet 변환 세부 처리

### 처리 내용

- `?` 값 → `null`
- 시간 값 → millisecond 단위 timestamp
- 측정값 → `float32`
- 압축 방식 → ZSTD

### 시간 값 처리 문제

원본 시간 예시:

```text
2023-09-22 22:26:28.367
```

초기 PyArrow 시간 변환에서 millisecond 처리 문제가 발생함.

### 해결

- 시간 문자열을 초 단위와 millisecond 부분으로 나눠 처리
- Python 반복문이 아닌 PyArrow 연산을 사용해 성능 저하를 최소화

## 7-2. Spark 관련 세부 사항

### 현재 역할

- 초기 CSV → Parquet 변환 단계에서는 사용하지 않음
- 이후 분산 처리 단계에서 사용 예정

### 예정 작업

- 전체 데이터 상태 검사
- 가구별 채널 시간 정렬
- 채널 간 결합
- 학습용 데이터 생성
- worker 수에 따른 처리시간 비교
