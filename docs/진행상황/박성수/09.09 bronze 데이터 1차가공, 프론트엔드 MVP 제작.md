# bronze 데이터 1차 가공, 전체 데이터 HDFS 적재 테스트

## 1-1. 목표

- 5.8TB 규모 데이터를 제한된 저장 공간에서 처리
- HDFS/Spark 기반 분산 저장 구조 구성
- 전체 원본을 한 번에 풀지 않고 순차 처리할 수 있는 방식 마련

## 1-2. 초기 구조와 문제

초기에는 아래 구조로 진행했다.

```text
압축 원본
→ 채널별 압축 해제
→ gzip
→ HDFS
→ Spark에서 CSV 처리
→ Parquet 저장
```

| 확인된 문제    | 내용                                                           |
| -------------- | -------------------------------------------------------------- |
| 저장 공간 부족 | 전체 압축 해제 시 약 5.8TB로, 각 노트북에 모두 보관하기 어려움 |
| 네트워크 병목  | 실제 전송 속도가 약 80~100Mbps 수준                            |
| 전송량 과다    | 첫 채널 기준 6.03GiB CSV → gzip 1.35GiB                        |
| 중복 처리      | HDFS에 저장한 CSV/gzip을 Spark가 다시 읽고 Parquet으로 재저장  |

## 1-3. 해결 방향

### 로컬에서 Parquet 변환 후 HDFS 저장

```text
압축 원본
→ 채널별 압축 해제
→ CSV 형식 정리
→ ZSTD Parquet 변환
→ HDFS 저장
```

- 첫 채널 기준:
  - CSV: **6.03GiB**
  - gzip: **1.35GiB**
  - Parquet: **0.99GiB**
- HDFS 전송 전 데이터 크기를 먼저 줄여 네트워크 부담 완화

### 채널 단위 순차 처리

```text
채널 압축 해제
→ 변환
→ 저장
→ CSV 삭제
→ 다음 채널
```

- 전체 5.8TB를 동시에 저장하지 않도록 변경

### 재시작 구조 추가

- 압축 해제 완료
- Parquet 변환 완료
- HDFS 업로드 완료
- 최종 저장 완료

단계별 상태를 기록해 중단 후 이어서 처리할 수 있도록 구성

## 1-4. 9/9 결과 및 한계

### 결과

- 전체 CSV를 한 번에 저장해야 하는 문제 해결
- HDFS 전송량 감소
- Spark에서 CSV를 다시 처리하는 중복 작업 제거
- 작업 재시작 가능 구조 마련
- 실제 병목이 네트워크라는 점 확인

### 한계

- 30Hz Parquet 전체도 여전히 수백 GB 규모
- 현재 네트워크에서는 HDFS 적재 시간이 길음
- 저장 공간 때문에 HDFS 복제 수를 1로 사용 중
- 분산 저장의 장점을 충분히 활용하기 어려움

## 1-5. SSH 및 접근 보안

### 적용 방향

- 개인 노트북 5대를 이용하는 환경이므로 불필요한 외부 접근을 줄이는 방향으로 구성
- 작업 노드(worker)는 **`master-ss`에서 관리하는 구조**로 정리
- 작업 노드에 대한 SSH 접근 범위를 제한해 임의 접근 가능성을 줄임
- 비밀번호 기반 접근보다는 **키 기반 접속 중심**으로 운영하는 방향 적용

## 1-6. HDFS 기본 설정

### 현재 기준

- 블록 크기: **256MiB**
- 초기 복제 수: **1**
- DataNode: worker 4대
- `master-ss`: NameNode만 사용

### 복제 수를 1로 둔 이유

- 30Hz Parquet 전체 예상 크기가 수백 GB 규모
- 각 노트북의 저장 공간이 약 500GB 수준으로 제한
- 우선 전체 데이터를 저장할 수 있는 구조를 만드는 것이 목적

### 향후

- 1Hz로 축소해 전체 크기가 충분히 작아지면 **복제 수 2 이상** 적용 검토
- DataNode 한 대가 중단돼도 데이터 읽기가 가능한지 확인 예정

# 프론트엔드 MVP

## 목표

- MVP 시연을 위한 **On:마음 안심 알림 웹 화면** 구현
- 사용자가 자신의 휴대폰에 push 알림을 등록한 뒤 위험상황 감지 알림
- 위험상황에 대한 응답을 서버로 전송

## 구현 완료 내용

MVP 핵심 시나리오인 **알림 등록 → 이상 감지 알림 수신 → 사용자 응답** 흐름을 시연할 수 있는 프론트엔드 구성 완료

- 브라우저 알림 권한 및 구독 상태 표시
- VAPID 공개키를 이용한 웹 푸시 구독 등록
- 백엔드의 푸시 구독 등록 API 연동
- Service Worker 기반 푸시 알림 수신
- 알림의 `예`·`아니오` 버튼을 통한 응답 API 연동
- manifest, icon 등 PWA 기본 세팅
- 알림 미지원, 권한 차단, 요청 실패 등에 대한 안내 메시지 처리

## MVP 시연 흐름

1. 사용자가 On:마음 웹 페이지에 접속
2. `알림 등록하기` 버튼을 눌러 브라우저 알림 권한을 허용
3. 프론트엔드가 생성한 푸시 구독 정보를 백엔드에 등록
4. 이상 생활 패턴이 감지되면 사용자의 기기로 알림이 전달
5. 사용자는 알림에서 `예` 또는 `아니오`를 선택해 바로 응답

## 시연 전 확인 사항

- 프론트엔드와 백엔드에 동일한 VAPID 공개키 설정
- 푸시 구독 및 알림 응답 API 연결 상태 확인
- 웹 푸시 사용을 위한 HTTPS 환경 또는 `localhost` 사용
- 모바일 기기에서 알림 권한 허용 여부 확인
