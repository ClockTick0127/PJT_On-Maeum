# 프론트엔드 환경설정 가이드

프론트 개발자가 로컬에서 실행하고, API·Keycloak 주소를 어떻게 다뤄야 하는지 정리한다. 배포 파이프라인(Jenkins, EC2 Compose)의 전체 구조는 `로컬_EC2_Compose_Jenkins_구조.md`를 참고한다.

기준 코드: `frontend/Dockerfile`, `frontend/nginx.conf`, `frontend/vite.config.ts`, `infrastructure/local/compose.yaml`, `infrastructure/ec2-a/compose.yaml`, `infrastructure/nginx/default.conf.template`, `infrastructure/frontend-build.env.example`.

## 1. 실행 방법

### 1-1. Vite dev 서버 (기본)

백엔드 인프라만 Docker로 띄우고 프론트는 로컬 Node로 실행한다.

```powershell
cd infrastructure/local
docker compose up -d
```

```powershell
cd frontend
npm ci
npm run dev
```

`http://localhost:5173`으로 접속한다. `vite.config.ts`의 proxy가 `/api` 요청을 `localhost:8080`(api-gateway)으로 넘긴다.

### 1-2. Docker 컨테이너로 실행

빌드 결과물을 nginx 이미지에 넣어 배포와 같은 형태로 확인할 때 사용한다. `frontend` 서비스는 프로필로 분리되어 있어 `--profile`을 붙여야 뜬다. `--profile`은 `up` 뒤가 아니라 `docker compose` 바로 뒤에 온다.

```powershell
cd infrastructure/local
docker compose --profile frontend up -d --build
```

`http://localhost:3000`으로 접속한다. Kafka UI까지 함께 띄우려면 `--profile tools`를 추가한다.

### 1-3. 포트 정리

| 용도 | 로컬 주소 | 운영 주소 |
| --- | --- | --- |
| 프론트 (Vite dev) | `http://localhost:5173` | 없음 |
| 프론트 (Docker nginx) | `http://localhost:3000` | `https://<APP_DOMAIN>` |
| API Gateway | `http://localhost:8080` | 프론트 nginx가 `/api/`로 프록시 |
| Keycloak | `http://localhost:8090` | `https://<AUTH_DOMAIN>` |

운영에서 포트가 안 보이는 이유는 nginx가 표준 포트 80/443을 그대로 쓰기 때문이다. 로컬은 80 포트 충돌을 피하기 위해 3000으로 매핑한다. 컨테이너 내부는 둘 다 80이다.

## 2. API 호출 규칙: 상대 경로만 쓴다

API 요청은 항상 `/api/...`로 시작하는 상대 경로로 보낸다. 호스트를 환경변수로 넣지 않는다.

```ts
// O
fetch('/api/devices')

// X
fetch(`${import.meta.env.VITE_API_URL}/api/devices`)
```

브라우저는 상대 경로를 현재 주소창의 origin에 붙여서 요청한다. 세 환경 모두 "프론트를 서빙한 서버가 `/api/`도 받아준다"는 구조라 코드와 빌드 결과물이 동일하다.

| 환경 | 주소창 | 실제 요청 | `/api/`를 처리하는 곳 |
| --- | --- | --- | --- |
| Vite dev | `localhost:5173` | `localhost:5173/api/devices` | `vite.config.ts` proxy → `localhost:8080` |
| 로컬 Docker | `localhost:3000` | `localhost:3000/api/devices` | `frontend/nginx.conf` → `api-gateway:8080` |
| 운영 | `https://<APP_DOMAIN>` | `https://<APP_DOMAIN>/api/devices` | `infrastructure/nginx/default.conf.template` → `api-gateway:8080` |

절대 URL을 쓰면 환경별로 이미지가 갈라지고, 다른 origin 취급이 되어 CORS 처리가 추가로 필요해진다. 상대 경로면 둘 다 발생하지 않는다.

## 3. Keycloak 주소는 주입이 필요하다

로그인은 브라우저가 Keycloak 로그인 페이지로 **직접 이동**하는 방식(Authorization Code + PKCE)이다. `/api/`처럼 nginx 뒤에 숨길 수 없으므로 프론트가 Keycloak 주소를 알아야 한다.

| 값 | 로컬 | 운영 | 출처 |
| --- | --- | --- | --- |
| Keycloak URL | `http://localhost:8090` | `https://<AUTH_DOMAIN>` | compose `.env`의 `KEYCLOAK_HOSTNAME` / `AUTH_DOMAIN` |
| realm | `nilm` | `nilm` | `infrastructure/keycloak/nilm-realm.json` |
| clientId | `nilm-dashboard` | `nilm-dashboard` | 같은 파일, public client |

주입 방식은 두 가지다.

### 3-1. Vite 환경변수 (단순)

`frontend-build.env`에 `VITE_KEYCLOAK_URL`, `VITE_KEYCLOAK_REALM`, `VITE_KEYCLOAK_CLIENT_ID`를 넣고 코드에서 `import.meta.env.VITE_*`로 읽는다. 값이 빌드 시점에 JS에 박히므로 로컬과 운영 이미지가 달라진다. 빨리 붙일 때 적합하다.

### 3-2. 런타임 주입 (권장)

이미지에는 주소를 넣지 않고, nginx가 `/config.json` 같은 엔드포인트로 값을 내려준다. 프론트는 시작 시 이를 fetch해서 Keycloak 클라이언트를 초기화한다. 운영 nginx 템플릿은 이미 `AUTH_DOMAIN`을 envsubst로 받고 있어 확장이 자연스럽고, 이미지 하나로 로컬·운영을 모두 커버한다. 이 방식을 쓰면 `frontend-build.env`에 Keycloak 주소를 넣을 필요가 없다.

어느 방식이든 아래 값이 서로 맞아야 로그인이 동작한다.

- `FRONTEND_ORIGIN`: realm import 시 `nilm-dashboard`의 redirect URI(`${FRONTEND_ORIGIN}/*`)와 web origin으로 들어간다. 로컬 `.env.example`은 `http://localhost:5173`이므로 Docker 프론트(3000)에서 로그인하려면 값을 바꾸고 Keycloak을 재import해야 한다. 운영은 `https://<APP_DOMAIN>`.
- `KEYCLOAK_HOSTNAME`: 토큰의 issuer가 된다. 프론트가 쓰는 Keycloak URL과 같아야 한다.
- `JWT_ISSUER_URI`: 백엔드가 토큰 issuer를 검증하는 값. `<KEYCLOAK_HOSTNAME>/realms/nilm`이어야 한다.
- `CORS_ALLOWED_ORIGINS`: 백엔드 CORS 허용 목록. 로컬은 5173과 3000이 이미 들어 있다.

현재 화면에는 로그인 UI가 없다. 운영 Keycloak 사용자 생성 등은 `Keycloak_운영환경_설정.md`를 따른다.

## 4. frontend-build.env 만들기

Vite 빌드 시점에 필요한 공개 변수를 담는 파일이다. **`infrastructure/frontend-build.env.example`을 복사해서 만든다.**

```powershell
Copy-Item infrastructure/frontend-build.env.example infrastructure/frontend-build.env
```

규칙:

- `VITE_` 접두어가 붙은 값만 넣는다. 그 외 변수는 Vite가 무시한다.
- **비밀 값을 넣지 않는다.** `VITE_*` 값은 빌드된 JS에 그대로 포함되어 브라우저에서 누구나 볼 수 있다. Keycloak public client의 clientId처럼 노출되어도 되는 값만 허용된다.
- `*.env`는 `.gitignore`에 걸려 커밋되지 않는다. `.env.example`만 커밋한다. 새 변수를 추가하면 example 파일에도 키를 적어 둔다.
- 2장에서 설명한 대로 API 주소는 넣지 않는다.

### 4-1. 빌드에 들어가는 경로

| 단계 | 동작 |
| --- | --- |
| Jenkins | `FRONTEND_ENV_CREDENTIAL` 파라미터에 Secret file credential(`frontend-build-env`) ID를 지정하면 `master` 브랜치 빌드에서 파일을 내려받아 `FRONTEND_ENV` 변수로 넘긴다. 비워 두면 변수 없이 빌드한다. |
| `infrastructure/scripts/build.sh` | `FRONTEND_ENV`가 있으면 `--secret id=frontend_env,src=<파일>`과 해시 build-arg를 붙여 `docker build`한다. |
| `frontend/Dockerfile` | secret을 `/app/.env.production`으로 마운트한 채 `npm run build`를 실행한다. 파일은 이미지 레이어에 남지 않는다. |

로컬에서 Docker 프론트를 띄울 때(`docker compose --profile frontend up --build`)는 secret을 넘기지 않으므로 `VITE_*` 값이 비어 있는 상태로 빌드된다. 로컬 Docker 빌드에서도 값이 필요하면 `frontend` 폴더에서 직접 빌드한다.

```powershell
docker build --secret id=frontend_env,src=infrastructure/frontend-build.env -t nilm-frontend frontend
```

### 4-2. Vite dev 서버에서 쓰기

dev 서버는 `frontend-build.env`를 읽지 않는다. `frontend/.env.local`에 같은 `VITE_*` 값을 넣으면 `npm run dev`가 읽는다. `frontend/.gitignore`가 `.env*`를 제외하므로 커밋되지 않는다.

```powershell
Copy-Item infrastructure/frontend-build.env frontend/.env.local
```

## 5. 자주 하는 실수

- `docker compose up -d --profile frontend`: `--profile` 위치가 틀려 frontend가 뜨지 않는다. `docker compose --profile frontend up -d`로 쓴다.
- `.env`(compose용)와 `frontend-build.env`(Vite용)를 혼동한다. 전자는 `infrastructure/local/.env`로 컨테이너 런타임 값, 후자는 프론트 빌드 시점 값이다.
- API 주소를 `VITE_API_URL`로 넣는다. 상대 경로로 충분하고, 넣으면 환경별 이미지가 갈라진다.
- Docker 프론트(3000)에서 로그인이 redirect 오류로 실패한다. `FRONTEND_ORIGIN`이 5173으로 import되어 있기 때문이다.
